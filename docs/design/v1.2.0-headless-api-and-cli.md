# Design: the headless API and the `jura` CLI for v1.2.0

**Deliverable**: W37-1
**Status**: Design. Nothing here is implemented.
**Date**: 10 September 2026
**Specification**: `backlog/BL-API-001-the-headless-api-is-documented-and-does-not-exist.md`
**Release**: v1.2.0, per `~/jura-brain/decisions/2026-09-10-trace-follow-up-release-is-v120.md`

Every claim below about the current state of the tree names the file it came
from, or the command that produced it. The commands are collected in the last
section so they can be re-run.

---

## 1. What this decides, in one page

1. The REST API stays where it is, in process, behind the existing `api` cargo
   feature. It gains a second binary target, `jura-trace-api`, in the same
   crate, and that binary owns the Python sidecar's lifecycle through a new
   Tauri-free supervisor module shared with the desktop build.
2. The CLI is `jura`, a thin REST client over that API, and it lives in this
   repository as a Cargo workspace member rather than in its own repository.
3. The default bind is `127.0.0.1`. A non-loopback bind is possible, requires
   an explicit second flag, and refuses to start without an API key. The
   documentation that says exposure is impossible is rewritten rather than
   quietly contradicted.
4. A verification that completes exits `0` whatever it found. Verdicts reach
   the exit code only through an explicit `--fail-on`, which uses a code far
   away from the error range so that "suspicious" can never be mistaken for
   "broken".
5. `--format json` prints the API response body verbatim, so there is one
   schema and one version field rather than two.
6. Watermarking, video and audio, `jura watch`, TLS, a TOML configuration file
   and a separate server distribution are all out of scope, and section 8 says
   why for each.
7. Five to six engineer-days delivers a working headless binary and a `jura
   verify` that scripts can rely on. Ten days adds `jura sign`, batch NDJSON
   output, a Linux server tarball and the full test rig.

## 2. What exists today

### 2.1 The Axum surface is real, compiled by default, and tested

`src-tauri/src/api/` is 2,179 lines across six files:

```
src-tauri/src/api/auth.rs         152
src-tauri/src/api/error.rs        169
src-tauri/src/api/mod.rs          302
src-tauri/src/api/rate_limit.rs   259
src-tauri/src/api/routes.rs      1116
src-tauri/src/api/types.rs        181
```

The `api` feature is not optional in practice. `src-tauri/Cargo.toml:114`
reads `default = ["custom-protocol", "api"]`, and `:116` expands `api` to
`["axum", "tower", "tower-http", "utoipa", "utoipa-swagger-ui", "dashmap",
"tokio"]`. Every shipped build therefore carries the server.

It compiles. `cargo check --all-targets` in `src-tauri/` exits 0 (section 12,
command 3). The twenty integration tests in
`src-tauri/tests/api_integration.rs` all pass in 2.08 seconds (command 4).

Routes registered at `src-tauri/src/api/mod.rs:205-224`:

```
GET    /api/v1/health
POST   /api/v1/verify
POST   /api/v1/verify/url
POST   /api/v1/verify/batch
POST   /api/v1/protect/sign
POST   /api/v1/protect/fingerprint
POST   /api/v1/protect/watermark/embed
POST   /api/v1/protect/watermark/extract
POST   /api/v1/claims/check
GET    /api/v1/stats
POST   /api/v1/auth/keys
GET    /api/v1/auth/keys
DELETE /api/v1/auth/keys/{key_id}
GET    /openapi.json
GET    /swagger-ui         (redirect)
GET    /swagger-ui/        (HTML)
```

Authentication is `Authorization: Bearer jt_<key>`, SHA-256 hashed and checked
against the `api_keys` table (`src-tauri/src/api/auth.rs:33-84`). Health,
`/openapi.json` and `/swagger-ui*` bypass it (`:44-49`). Rate limiting is a
per-key token bucket with a 60 second refill period
(`src-tauri/src/api/rate_limit.rs:6`, `:49`).

### 2.2 It starts in exactly one place, and only with a window

`src-tauri/src/lib.rs:4644-4677`, inside the Tauri `setup()` closure. It
bootstraps a first API key via `db.ensure_bootstrap_api_key()` (`:4654`) and
then calls `api::start_server(api_state, 8300)` (`:4675`). There is no other
call site. `src-tauri/src/main.rs` is eight lines and parses nothing.

BL-API-001 is right that the binary parses no arguments: `grep` for `clap` and
`argh` across `src-tauri/` returns nothing, and `std::env::args` appears once,
in `src-tauri/src/bin/gen_detectors.rs:284`.

### 2.3 The sidecar is spawned through Tauri, which is the real blocker

`spawn_sidecar` at `src-tauri/src/startup.rs:313` takes `&tauri::AppHandle` and
reaches the child through `app.shell().sidecar("jura-sidecar")`. It also uses
`app.path().resource_dir()` to set `JURA_MODELS_DIR`. Neither is available
without a built Tauri application, and `tauri::generate_context!` refuses to
compile unless `frontendDist` exists (section 12, command 2). A headless binary
cannot use this function as written.

Everything else it does is portable and must be kept:

- `kill_orphan_sidecars()` at `startup.rs:208`, `pkill -KILL -f jura-sidecar`
  on Unix and `taskkill /F /IM jura-sidecar.exe` on Windows.
- `cleanup_stale_mei_dirs()` at `startup.rs:285`, which removed 3.5 GB of
  stale PyInstaller extraction directories on the developer machine in May.
- `wait_for_sidecar_ready()` at `startup.rs:448`, currently
  `#[allow(dead_code)]`, whose own doc comment says it is "retained for future
  single-shot callers (e.g. v1.0.1 `jura` CLI's `--wait-ready` flag)".
- `pick_ephemeral_port()` at `startup.rs:487`.

The good news is that `AppState` itself needs no Tauri handle. The existing
test harness builds one from a temp SQLite file and a `SidecarClient` and
nothing else (`src-tauri/tests/api_integration.rs:30-57`), and
`verify_content_inner` takes `(&str, &str, Option<&str>, &Mutex<AppState>)`
(`src-tauri/src/verify/pipeline.rs:491-496`). The verification engine is
already headless. Only process management is not.

### 2.4 The sidecar's own HTTP surface

Thirty-one FastAPI routes, entry point `sidecar/main.py`, app constructed at
`main.py:120-128` with `docs_url=None, redoc_url=None, openapi_url=None`.
Readiness is `GET /health/ready`, a constant-time flag read
(`sidecar/app/api/health.py:31-44`); capability detail is `GET /health`
(`:47-125`). Everything else is under `/forensics` and `/ollama`.

Authentication is a single shared secret in the `X-Jura-API-Key` header,
enforced by middleware at `sidecar/main.py:148-186` and scoped to paths
starting with `/forensics` (`:166`). The secret is `JURA_SIDECAR_KEY`,
defaulting to the empty string (`sidecar/app/config.py:38`). The Rust side
generates 256 bits of it per session in release builds and passes it to the
child through the inherited environment (`src-tauri/src/lib.rs:4194-4223`).

Two facts matter for a headless mode:

- With no key set and no pytest running, `/forensics/*` returns **503**, not
  200 (`sidecar/main.py:174-178`). A headless supervisor must therefore mint a
  key and export it before spawning, exactly as the desktop does.
- **JTV-205, the auth carve-out**, is `sidecar/main.py:168-172`: if
  `PYTEST_CURRENT_TEST` is in the environment, authentication is skipped
  entirely. It is recorded at `docs/release/v1.1.0-plan.md:144` and confirmed
  not started at `docs/release/v1.1.0-checkpoint-2026-09-10.md:87`. It is a
  test-visibility problem for this work, not a production hole, and section 6
  says what the headless design does about it.

The sidecar has no shutdown endpoint, no SIGTERM handler, no `atexit` and no
parent-process watchdog. Its `lifespan` at `sidecar/main.py:33-114` has no code
after `yield`. If the parent dies, it survives. The desktop compensates by
killing the child in `RunEvent::Exit` (`src-tauri/src/lib.rs:4761`) and by
reaping orphans on the next launch. A headless binary must do both.

Cold start is the dominant cost. The bundle on this machine is 529 MB
(command 5). The measured figures on record are 39 seconds for `--onedir`
against 90 or more for `--onefile` (`CHANGELOG.md:324`), with Windows
`--onefile` at 90 to 200 seconds on every cold start
(`docs/release/v1.1.0-plan.md:215`). `scripts/smoke_test_frozen_sidecar.py`
allows a 240 second ceiling. Only Apple Silicon builds `--onedir` today
(`.github/workflows/release.yml:578`).

## 3. Decision 1: what ships as the API

### 3.1 The endpoint set

v1.2.0 ships the surface that exists, corrected, plus two additions. Nothing
new is invented.

**Kept as is** (already implemented, already tested):

```
GET    /api/v1/health
POST   /api/v1/verify
POST   /api/v1/verify/url
POST   /api/v1/verify/batch
POST   /api/v1/protect/fingerprint
POST   /api/v1/protect/sign
GET    /api/v1/stats
POST   /api/v1/auth/keys
GET    /api/v1/auth/keys
DELETE /api/v1/auth/keys/{key_id}
GET    /openapi.json
GET    /swagger-ui/          (assets served locally, see 3.4)
```

**Added**:

```
GET    /api/v1/ready
```

```json
{
  "data": {
    "server": "ready",
    "sidecar": "ready",
    "sidecarSince": "2026-11-02T09:14:07Z",
    "sidecarPort": 51873,
    "detail": null
  },
  "apiVersion": "1.0",
  "degraded": false
}
```

`sidecar` is one of `starting`, `ready`, `absent`, `failed`. This exists
because `GET /api/v1/health` is expensive: it calls
`SidecarClient::is_available()`, which is a 10 second timeout across two
attempts (`src-tauri/src/sidecar.rs:1001-1023`). A supervisor or a CI job
polling that endpoint every second is not polling, it is queueing. `ready`
reads a cached state that the supervisor writes, mirroring the sidecar's own
cheap `/health/ready`.

The cached flag is the exact shape BL-SILENT-001 warns about, so it carries
two obligations. The supervisor updates it on child process exit as well as on
readiness, so a dead sidecar reports `failed` and not a stale `ready`. And the
test in section 10 kills the sidecar out from under a running server and
asserts the endpoint changes within one poll interval.

**Added to every verify response**: a `verdict` block.

```json
"verdict": {
  "band": "uncertain",
  "score": 0.55,
  "ceilingApplied": "deepfakeInconclusive",
  "bandBoundaries": { "trusted": 0.7, "uncertain": 0.4 }
}
```

`band` is one of `trusted`, `uncertain`, `untrusted`. This is not decoration.
Today the band is computed in the frontend and nowhere else:
`ui/src/lib/types.ts:1196-1200` maps the score at 0.7 and 0.4, and
`ui/src/lib/components/VerdictSummary.svelte:20-27` then forces `high` down to
`medium` when the deepfake detector returned `inconclusive` or `synthetic`.
A CLI that computed a band from `overallTrust` alone would disagree with the
screen on exactly the files that matter most. Moving the whole rule into Rust,
and having the frontend consume the same field, is the only version of this
that cannot drift.

**Removed from the compiled surface**: the two watermark routes, behind a new
`watermark` cargo feature that is off by default. `ui/src/lib/featureFlags.ts`
sets `V1_SHOW_WATERMARK = false`, BL-WM-001 records the embed and extract paths
as bit-incompatible, and the release decision of 10 September puts watermarking
in v1.3.0. An OpenAPI document that advertises `/protect/watermark/embed` is
advertising a feature the product says it does not have. Compiling them out is
cheaper than documenting them as unsupported and more honest than leaving them
undocumented, which is where they are now.

### 3.2 Where the documentation was wrong, and what happens to it

Rows 3, 4, 13 and 14 of the table in section 2.5 are documentation faults, not
implementation faults. The implementation is the contract, because
`docs/API_WRAPPER.md:705` declares the response shape a public API contract
from v1.0, real integrations were built against the running server (the C2PA
conformance evidence bundle at
`docs/c2pa-conformance/evidence-bundle/SUMMARY.json:27` explicitly records
"camelCase, detectorsRun, deepfakeResult"), and changing the wire format to
match a document nobody implemented would break them. So: **the document is
rewritten to camelCase and to the `data` envelope. The wire format does not
move.**

Rows 5, 7 and 8 are different, because they describe request parameters a
reader would actually send, and the server ignores them in silence. Every
worked example in `docs/API_WRAPPER.md` uses `?mode=deep`
(`:271`, `:837-855`, the Python example at `:807`, the Moodle example at
`:892`). Anyone following those examples has been getting whatever the default
is, not what they asked for. This is the BL-SILENT-001 shape in the request
path, and it gets the BL-SILENT-001 treatment:

- `mode` is accepted as a query parameter as well as a form field. The form
  field wins if both are present, and disagreement between them is a 400.
- `mime_type` and `concurrency` return `400` with a message naming the
  parameter and saying it is not implemented. A caller who sends them learns
  so on the first request rather than through a wrong answer.
- Other unknown query parameters are ignored, because rejecting everything
  unknown is the kind of strictness that breaks clients on an additive change.

Row 6, the default mode, keeps the implementation. The comment at
`src-tauri/src/api/routes.rs:120-123` records that `deep` was chosen so the
REST API exercises the full ten-detector automatic pipeline and matches the
user-facing claim, following a smoke test on 2026-06-01. Changing it to
`standard` to match a document would silently reduce the analysis every
existing integration receives. The document changes.

Row 11, `PATCH /api/v1/auth/keys/{id}`, is deleted from the document rather
than implemented. It exists in the document only to serve the Enterprise
per-key rate limit story at `API_WRAPPER.md:790-799`, and section 6 changes
what rate limiting is for.

Rows 15 and 16 are corrected in the document to per-minute and 200 MB.

### 3.3 Request and response shapes the CLI depends on

```
POST /api/v1/verify
Authorization: Bearer jt_<key>
Content-Type: multipart/form-data

file:  <binary>            required
mode:  quick|standard|deep  optional, default deep
```

```json
{
  "data": {
    "sourceType": "upload",
    "contentType": "image",
    "mode": "deep",
    "overallTrust": 0.55,
    "verdict": { "band": "uncertain", "score": 0.55, "ceilingApplied": "deepfakeInconclusive" },
    "inputSha256": "9f2c...",
    "detectorsRun": ["exif_anomaly", "c2pa", "ela", "noise", "copy_move", "deepfake", "clip", "jpeg_ghost", "segmented_ela", "colour_temperature"],
    "provenance": {
      "engineVersion": "1.2.0",
      "sidecarVersion": "1.2.0",
      "modelHashes": { "deepfakeClassifier": "3a91...", "univfdProbe": "c04e..." },
      "verificationMode": "deep",
      "timestampUtc": "2026-11-02T09:15:44Z"
    }
  },
  "apiVersion": "1.0",
  "degraded": false
}
```

`provenance` and `detectorsRun` already exist
(`src-tauri/src/verify/types.rs:218-222`, `:259`). They are named here because
they are the two fields that make a scripted result auditable, and the CLI's
text output leads with them.

Errors keep the existing envelope and gain discriminating codes, which
section 7 needs:

```json
{ "code": "UnsupportedFormat", "message": "image/bmp is not supported by the verification pipeline" }
```

Today `src-tauri/src/api/error.rs:72-74` returns the single code `BadRequest`
for a malformed multipart body, a missing `file` field and an empty uploaded
file alike. Three different caller mistakes with one code and one status is
not enough to build an exit-code contract on.

### 3.4 Swagger UI

`/swagger-ui/` serves the assets vendored by `utoipa-swagger-ui`, which is
already a dependency and already compiled. No CDN, no unpinned script. This
closes SR-24 and JTV-209 and removes the fifth row of BL-CLAIM-001's egress
table, which shortens the README sentence that item is waiting on.

Rejected: dropping the Swagger page behind `#[cfg(debug_assertions)]`, which
the audit offered as an alternative at
`docs/security-audit-2026-05-16.md:312`. A browsable local API document is
exactly the thing that makes a headless API adoptable by someone evaluating
it, and the whole point of this deliverable is adoption. Vendoring costs
nothing extra because the crate is already there.

## 4. Decision 2: how it runs

### 4.1 The shape

**A second binary target in the existing crate, sharing the library.**

```toml
[[bin]]
name = "jura-trace-api"
path = "src/bin/jura_trace_api.rs"
required-features = ["api"]
```

```bash
jura-trace-api                              # 127.0.0.1:8300, spawns the sidecar
jura-trace-api --port 8400 --wait-ready
jura-trace-api --no-sidecar                 # Rust-only detectors, degraded by design
jura-trace-api keys add --name ci           # mints a key, prints it once, exits
jura-trace-api keys list
```

The binary does four things the library does not do today: parse arguments,
own the sidecar's lifecycle, fail loudly on a bind error, and shut the sidecar
down on a signal.

### 4.2 The alternatives, and why they lost

**A separate crate outside this workspace.** Rejected. It would need its own
copy of `AppState`, `db`, `sidecar`, `verify` and `c2pa`, or a published
library crate to depend on. The whole verification engine is
`jura_trace_lib`, and the integration tests already prove it can be driven
without Tauri (`src-tauri/tests/api_integration.rs:30-57`). A second crate
buys isolation nobody needs and guarantees drift.

**Implementing `--api` on the desktop binary**, as `docs/API_WRAPPER.md:98`
promises. Rejected, and the documentation line is deleted. The flag would be a
no-op that turns on something already on: the API starts unconditionally at
`src-tauri/src/lib.rs:4675` whenever the window runs. Adding argument parsing
to a Tauri binary also means handling the `-psn_*` argument macOS passes to
bundled applications and the Windows subsystem attachment, for a flag with
nothing to switch. BL-API-001 offers implementing or deleting as the two
options; deleting is correct.

**Booting a windowless Tauri application in the headless binary** so
`app.shell().sidecar()` keeps working. Rejected. It links the webview
framework into a server binary, needs a main-thread event loop on macOS,
produces a Dock icon, and `tauri::generate_context!` still requires
`frontendDist` to exist at compile time (proved in command 2). The supervisor
extraction in 4.3 is less work than any of that.

**Exposing the Tauri command surface over HTTP** rather than the Axum routes.
Rejected: it is what the Axum routes already are. `docs/API_WRAPPER.md:43`
calls the wrapper "a thin HTTP layer over existing Tauri commands", which is
approximately true, and there are seventy `#[tauri::command]` functions in
`src-tauri/src/lib.rs`. Most are database and settings operations with no
headless meaning. Publishing all seventy would be a bigger compatibility
surface than the thirteen routes, for less value.

### 4.3 The sidecar supervisor

A new module, `src-tauri/src/sidecar_supervisor.rs`, with no Tauri types in
its signature:

```rust
pub struct SidecarSupervisor { /* child, port, key, state */ }

impl SidecarSupervisor {
    pub fn spawn(binary: &Path, models_dir: Option<&Path>, port: u16, key: &str)
        -> Result<Self, SupervisorError>;
    pub fn wait_ready(&self, timeout: Duration) -> Result<(), SupervisorError>;
    pub fn state(&self) -> SidecarState;   // Starting | Ready | Absent | Failed
    pub fn shutdown(self) -> Result<(), SupervisorError>;
}
```

It uses `std::process::Command`. It reuses `kill_orphan_sidecars`,
`cleanup_stale_mei_dirs`, `wait_for_sidecar_ready` and `pick_ephemeral_port`
from `src-tauri/src/startup.rs` by moving them into the new module and having
`startup.rs` call across. The desktop path then differs from the headless path
only in how it resolves the binary path and in the fact that it keeps a
`tauri_plugin_shell` child handle for `RunEvent::Exit`. Stage 1 in section 9
includes converting the desktop to the shared supervisor, because two
implementations of process management is how the sidecar becomes an orphan
again.

**Resolving the sidecar binary.** In order: `--sidecar-binary <path>`; then
`JURA_SIDECAR_BINARY`; then next to the running executable, which is where the
macOS launcher stub lives (`src-tauri/binaries/jura-sidecar-aarch64-apple-darwin`
is a 34 KB Mach-O that `execv`s
`../Resources/sidecar-bundle/jura-sidecar`); then the platform application
directory. If none resolves, the server starts anyway and reports
`sidecar: "absent"` on `/api/v1/ready`, and every verify response carries
`degraded: true`. It does not pretend.

**Cold start.** The bundle is 529 MB and the honest figure is tens of seconds,
up to 240 in the worst recorded case. Three consequences:

1. `jura-trace-api` spawns the sidecar at startup and returns from `main` into
   `serve` immediately. It does not block on readiness unless `--wait-ready` is
   given, which exists precisely so a CI job can say "wait, then run".
2. `--wait-ready` takes an optional timeout, default 300 seconds, and exits
   non-zero if it expires. A default of 60 would fail correctly-working Windows
   installations, per `docs/release/v1.1.0-plan.md:215`.
3. The CLI never spawns a server. `jura verify` against an unreachable API
   exits 2 with a message naming the command to start one. A CLI that quietly
   started a 529 MB process tree on first use, and left it running, is a worse
   surprise than an error message.

**Shutdown.** SIGINT and SIGTERM on Unix, and the Windows console control
handler, run `shutdown()`, which kills the child and waits for it. The
supervisor also runs `kill_orphan_sidecars()` before spawning, because the
sidecar has no watchdog of its own and this is the only mechanism that catches
a `kill -9`ed parent.

**One server, one sidecar.** If the desktop app is running, port 8300 is
taken, and `jura-trace-api` exits non-zero and says so. Section 6 covers why
that is a hard failure rather than the current warning.

**The database.** Default is the same file the desktop uses, resolved by
`dirs_next_data_dir()` (`src-tauri/src/startup.rs:32`), so a scripted
verification lands in the same library and the same audit log as a manual one,
which is the point for an evidence chain. `--db <path>` overrides it and
`--ephemeral` uses a temporary database that is deleted on exit, which is the
Amara and Aisha field-operations requirement recorded in
`docs/decisions/jura-cli-binary-name-reservation.md:53`.

Sharing the file has a cost that must be paid in Stage 1. `src-tauri/src/db.rs:34`
sets `PRAGMA journal_mode=WAL` and nothing sets `busy_timeout`, so a writer
that meets another writer gets `SQLITE_BUSY` immediately instead of waiting.
Two processes on one database makes that reachable. `busy_timeout` is one line
and a test.

## 5. Decision 3: the CLI

### 5.1 Name and location

The binary is `jura`, per
`docs/decisions/jura-cli-binary-name-reservation.md:13`. That half of the
decision is unchanged and this document does not reopen it.

The repository half is restated. **The CLI lives in this repository as a Cargo
workspace member at `cli/`, not in `codeberg.org/jura-labs/jura-cli`.**
Reasons: W37-1 retires Codeberg, so the named repository will not exist;
`docs/decisions/auto-update-hosting-review.md:376` had already concluded
Codeberg cannot host the binaries; a thin client whose only contract is this
repository's JSON schema wants to be tested in the same CI run that can break
it; and a second repository doubles the release, signing and CI cost for
roughly 800 lines of Rust. The crate name `jura` on crates.io stays reserved
and is claimed when the CLI first ships publicly, which is not necessarily
v1.2.0 (section 8).

### 5.2 Commands in v1.2.0

```bash
jura verify <path>...                # 0 on completion, whatever the verdict
jura verify --url <url>
jura version                         # CLI, API and engine versions
jura auth set-key <key>              # stores in the OS keyring
jura auth show-key
jura auth status                     # is a key present, does it work
```

`jura sign` is in the ten-day version only (section 9). `jura batch`,
`jura watch` and export formats are out (section 8).

### 5.3 Configuration precedence

```
--api-url  <url>     >  JURA_API_URL  >  http://127.0.0.1:8300
--api-key  <key>     >  JURA_API_KEY  >  OS keyring  >  (none)
```

`JURA_API_URL` and `JURA_API_KEY` are chosen because they are already in the
tree: `scripts/agents/config.py:14` uses `JURA_API_URL` and
`docs/c2pa-conformance/evidence-bundle/README.md:224` uses `JURA_API_KEY`.
`scripts/build-sample-pack.sh:33` uses `JURA_API`, which is the odd one out and
which Stage 5 changes.

`--api-key` on the command line is accepted and documented as the least safe
option, because it lands in shell history and in the process table.

## 6. Decision 4: binding, authentication and what it refuses

### 6.1 The default

**`127.0.0.1:8300`.** Unchanged from `src-tauri/src/api/mod.rs:148`. This is
not a preference. `README.md:7` says "No data is uploaded to external
servers", the product is bought on that sentence, and BL-CLAIM-001 records
legal review reading an inaccurate version of it as a misleading action under
the DMCC Act 2024 s.226. A headless API that listened on `0.0.0.0` by default
would put an unauthenticated-until-you-configure-it forensics engine on the
local network, and it would do it to users who never asked for a server.

### 6.2 The opt-in, stated explicitly

```bash
jura-trace-api --bind 0.0.0.0 --allow-remote
```

Rules, all enforced at startup, before the listener is created:

- `--bind` alone with a non-loopback address is a **usage error**. The process
  exits 1 and says that `--allow-remote` is required. It does not fall back to
  loopback, because a server that silently binds somewhere other than where it
  was told is the same defect class as everything in BL-SILENT-001.
- `--allow-remote` refuses to start if the `api_keys` table has no active key.
  There is no unauthenticated remote mode and no `--no-auth`. The TOML
  `require_key = false` at `docs/API_WRAPPER.md:130` is deleted from the
  document along with the rest of the file that does not exist.
- On a successful non-loopback bind the process writes one warning line to
  stderr naming the address and the fact that traffic is unencrypted, and one
  entry to the audit log.
- TLS is out of scope (section 8). The documentation says to put a reverse
  proxy in front and to treat the listener as trusted-network-only.

`docs/API_WRAPPER.md:41` currently says "There is no configuration option to
expose it externally", and `:967` says any attempt to bind `0.0.0.0` "will
fail at startup". Both are true today and both stop being true. They are
rewritten rather than left to be discovered, which is the entire complaint in
BL-API-001 and in BL-CLAIM-002 before it.

The reason to allow it at all, rather than take the simpler line and refuse:
the documented audience is CI pipelines and background services
(`docs/API_WRAPPER.md:100`), a container cannot publish a port it has not bound
on `0.0.0.0`, and `sidecar/Dockerfile` already binds the sidecar that way. A
capability that the deployment target requires, refused on principle, gets
worked around with a socat wrapper and no warning line at all.

### 6.3 Authentication

Unchanged: `Authorization: Bearer jt_<key>`, SHA-256 in SQLite. It is
implemented, it is tested (`src-tauri/tests/api_integration.rs:171-230`), and
it is what the documentation and every existing script use.

What changes is that a key can be obtained without a graphical interface.
`jura-trace-api keys add --name ci` mints one, prints it once and exits, going
straight to `db.create_api_key` without starting a server. This is not a
convenience. As section 2.5 records, `V1_SHOW_API_KEYS = false` hides the
entire key panel, so there is at present no supported way for a Community user
to obtain the key that the running server already requires.

`POST /api/v1/auth/keys` still needs an existing key, which is correct and
stays.

### 6.4 Rate limiting

The token bucket stays, but its default changes for the headless binary:
`--rate-limit <n>` per key per minute, default **600**, where `0` disables it.
The desktop keeps 100.

100 per minute was chosen for a graphical client. A scripted sweep with `xargs
-P4` over a directory can exceed it during the fast-failure cases, and a caller
who hits 429 in the middle of a thousand-file run has no good recovery. The
limiter protects a single-user loopback service from a single user, which is
not a threat; it is retained mainly because it becomes meaningful the moment
`--allow-remote` is used, which is why `0` is allowed but is not the default.

### 6.5 The sidecar key, and JTV-205

`jura-trace-api` generates a 256-bit `JURA_SIDECAR_KEY` per session if one is
not set, exactly as `src-tauri/src/lib.rs:4194-4223` does, and exports it to
the child. Without it the sidecar returns 503 on every `/forensics` route
(`sidecar/main.py:174-178`), so a headless mode that skipped this would run,
report healthy, and produce Rust-only results. That is the failure this whole
document is meant to be allergic to.

This design does not fix JTV-205. It does constrain the tests: **no test in
this work may rely on the `PYTEST_CURRENT_TEST` bypass at
`sidecar/main.py:168-172`.** The end-to-end tests set a real key and assert a
401 without it. If JTV-205 is closed during v1.2.0 those tests keep passing
unchanged, and if it is not, they are not silently exercising a code path that
production never takes.

## 7. Decision 5: the exit-code contract

### 7.1 The table

Codes 0 to 6 are as published at `docs/API_WRAPPER.md:687-695` and in
`docs/decisions/jura-cli-binary-name-reservation.md:39`. Codes 7 and above are
new, which the published contract explicitly permits: "new codes may be added
at the end (≥ 7) but the existing assignments do not change"
(`docs/API_WRAPPER.md:1029`).

| Code | Name | Meaning |
|---|---|---|
| 0 | success | The command completed. For `verify`, an analysis was produced. **This includes an untrusted verdict.** |
| 1 | usage | Bad arguments, unknown subcommand, mutually exclusive flags |
| 2 | unreachable | Could not connect to the API |
| 3 | auth | No key, malformed key, or rejected key |
| 4 | file | Local input problem: missing, unreadable, empty, over the limit |
| 5 | format | The server rejected the content as unsupported |
| 6 | server | The server failed: HTTP 5xx |
| 7 | timeout | The request exceeded `--timeout`, or `--wait-ready` expired |
| 8 | incomplete | `--require-complete` was given and the response had `degraded: true` |
| 20 | verdict | `--fail-on` was given and the verdict met the threshold |

### 7.2 Suspicious is not broken

This is the question the contract exists to answer, and the answer is a
separation, not a code.

**Codes 1 to 8 mean no usable verification was produced.** Code 0 and code 20
both mean one was. A caller that only wants to know whether the tool worked
tests `-le 0` or `-eq 20`. A caller that wants the verdict either reads the
JSON or asks for it in the exit status:

```bash
jura verify photo.jpg --fail-on untrusted   # 20 when band == untrusted
jura verify photo.jpg --fail-on uncertain   # 20 when band is uncertain or untrusted
```

Without `--fail-on`, a file that scores 0.02 exits 0, and the caller reads
`data.verdict.band`. This is the default because a trust score is not a
boolean, the product's own interface refuses to render it as one, and a tool
that exits non-zero on a low score would be read by every CI system as "the
tool broke" the first time someone pointed it at a screenshot.

The number 20 is deliberately far from the error range. `grep`'s 1-for-no-match
convention is well precedented but collides here with usage errors, and
`clamscan`'s 1-for-found would collide too. A caller who mistakes 20 for an
error is making a visible mistake, not an invisible one.

### 7.3 Two corrections to the published contract

**Exit 6 no longer means "partial-availability degraded response".** The first
published table says it does (`docs/API_WRAPPER.md:694`); the second says 5xx
only (`:1039`). The second is right and the first was wrong. A degraded
response is an HTTP 200 with real results computed by the Rust detectors, and
mapping it to the same code as a server crash tells the caller to retry
something that will not change. Callers who need completeness ask for it, and
get code 8.

**Exit 5 follows the error `code` field, not the HTTP status.** The published
tables disagree about whether 5 is HTTP 422 (`:694`) or HTTP 400 (`:1038`), and
`:699` says the translation "follows the HTTP status, not the response body".
That rule cannot be implemented against this server, because
`src-tauri/src/api/error.rs:72-74` returns HTTP 400 for a malformed request, a
missing field and an empty file alike. Following the status would map an empty
file to the same code as a typo in a flag name. So the CLI reads
`error.code`, which `src-tauri/src/api/error.rs:22` already documents as
"machine-readable error code (stable across releases)", and falls back to the
status when the code is unrecognised. Stage 2 adds the codes that make this
work: `EmptyFile`, `MissingField`, `UnsupportedFormat`, `PayloadTooLarge`.

### 7.4 Worked examples

```bash
# Gate a newsroom pipeline on anything not clearly trusted.
if ! jura verify "$1" --fail-on uncertain --format json > result.json; then
  case $? in
    20) echo "verification produced a doubtful verdict, escalating"; escalate result.json ;;
     2) echo "jura-trace-api is not running"; exit 75 ;;   # EX_TEMPFAIL
     *) echo "jura failed: $?"; exit 70 ;;                 # EX_SOFTWARE
  esac
fi
```

```bash
# Archive every result and never fail the build on a verdict.
find corpus -type f -print0 \
  | xargs -0 -P4 -I{} sh -c 'jura verify "$1" --format json > "out/$(basename "$1").json"' _ {}
```

## 8. Decision 6: output formats and versioning

### 8.1 Formats

```
--format text     default. Human readable. Not a compatibility surface.
--format json     the API response body, verbatim, pretty printed.
--compact         with json, one line.
--format ndjson   ten-day version only. One object per input.
```

`text` looks like this:

```
photo.jpg
  verdict      uncertain (0.55)
  mode         deep
  detectors    10 run, 0 unavailable
  sha256       9f2c1e...
  engine       1.2.0   sidecar 1.2.0   deep   2026-11-02T09:15:44Z
  note         AI-detection ceiling applied: deepfake result inconclusive
```

Two rules on formats:

**The output format never depends on whether stdout is a terminal.** Tools
that switch on `isatty` behave differently in a shell and in CI, which is the
one place a difference is hardest to see and most expensive. `--format` is the
only thing that decides.

**`text` is explicitly not stable.** It is documented as human output that may
change in any release, so nobody parses it. Anything a script needs is in
`json`, and if something is missing from `json` that is a bug in the JSON.

### 8.2 Versioning

The JSON the CLI prints is the API response body, unchanged. There is no CLI
envelope, no second version number and no reserialisation. One schema, one
version field, `apiVersion`, which is already `"1.0"`
(`src-tauri/src/api/types.rs:51`) and is already asserted by
`src-tauri/tests/api_integration.rs:419`.

Rejected: wrapping the API body in a CLI envelope with its own
`cliSchemaVersion`. It would double the compatibility surface for no gain,
and the first time the two versions disagreed the caller would have to work
out which one governed which fields.

The compatibility rules are the ones already published at
`docs/API_WRAPPER.md:709-713` and they now bind the CLI too:

- Fields may be added. Clients must ignore unknown fields.
- Fields are not renamed within v1.x. Types do not change, and widening a
  `string` to `string | null` is a break.
- Removal needs one minor release of deprecation.
- `provenance.engineVersion` describes the engine. `apiVersion` describes the
  envelope. They are not the same number and never have been.
- Every schema change gets a `[schema]` line in `CHANGELOG.md`.

Section 10 turns the first three of those from a policy into a test.

## 10. Decision 8: the staged plan

Estimates are engineer-days for one person who knows this tree. The v1.1.0
plan carried this item at "~5 to 6 days"

| Stage | What | Days | Ships alone? |
|---|---|---|---|
| 0 | Rewrite `docs/API_WRAPPER.md` against reality: all twenty rows of section 2.5, both exit-code tables collapsed into one, front matter corrected, the fictional deployment modes and TOML section deleted | 0.5 | **Yes, and it should go first** |
| 1 | `sidecar_supervisor` module, Tauri-free. `jura-trace-api` binary: arguments, spawn, readiness, signals, shutdown, orphan reap, fatal bind error, `keys add`. Desktop converted to the shared supervisor. `busy_timeout` on the database | 2.0 | Yes. A headless API with no CLI is already useful to `curl` and to `scripts/agents/` |
| 2 | API corrections: `verdict` block computed in Rust and consumed by the frontend, `GET /api/v1/ready`, `mode` as a query parameter, 400 for `mime_type` and `concurrency`, discriminating error codes, locally served Swagger assets, watermark routes behind a feature | 1.0 | Yes, independently of 1 |
| 3 | `cli/` workspace member. `jura verify`, `version`, `auth`. Exit codes, formats, keyring | 2.0 | Needs 1 and 2 |

| 5 | Packaging: `jura` in the release matrix for three platforms, signing on macOS and Windows, README and a quickstart | 1.0 | Needs 3 |
| 6 | `jura sign`, `jura batch` with NDJSON, `--ephemeral`, a Linux server tarball, `--concurrency` on the batch endpoint | 2.5 | Needs 3 |

**The five-day version** is stages 0, 1, 2, 3 and half of 4: a headless binary
that owns the sidecar, a `jura verify` with the full exit-code contract and
JSON output, the Swagger CDN call removed, honest documentation, and the
subset of tests that runs in the existing `ci.yml` Rust job. It does not ship
`jura` binaries in the release, so the first users build it with `cargo
install --path cli`. That is acceptable for an audience that is, by
definition, comfortable with a shell, and it is what makes five days real
rather than optimistic.

**The ten-day version** adds the rest of stage 4, all of stage 5 and all of
stage 6: signed `jura` binaries on three platforms in the release, `jura
sign`, NDJSON batch output, the guard self-test, and the installed-product
test. That is the version an OSINT toolkit can list, because a toolkit lists
things a reader can install in one command.

**What drives the estimate up.** Stage 1 is the only stage with real unknowns:
Windows process-group signal handling and the `--onefile` cold start are both
places where a day can disappear. Converting the desktop to the shared
supervisor could surface a JTV-184 regression on macOS, which would be worth
finding and would not be free. Stage 5 depends on the release workflow, which
`docs/release/v1.1.0-checkpoint-2026-09-10.md` shows is already carrying
several open faults.

**What drives it down.** The Axum server, the authentication, the rate
limiter, the OpenAPI generation and twenty integration tests already exist and
pass. `wait_for_sidecar_ready` was written for this. `AppState` already
constructs without Tauri. Stage 2's Swagger fix uses a dependency that is
already compiled. This deliverable is mostly assembly.

## 11. Decision 9: how it is tested

`backlog/BL-SILENT-001-mechanisms-that-report-success-while-doing-nothing.md`
is the design input for this section. Its Cause B is that "success was defined
as 'the step exited 0', not 'the expected artefact exists and is valid'". Its
Cause D rule is "exit status first, pattern second". Its plan item 2 asks for
guard self-tests, and item 3 for prove-it-ran assertions with a floor.

The eight assertions below are written so that each one fails when the thing
does not work. Where an assertion could pass vacuously, the floor is named.

**A1. The bind address is what it says.** Assert the listener's local address
is `127.0.0.1`, and separately assert that binding `0.0.0.0:<same port>`
**succeeds** while the server is running. If the server had taken the
wildcard, the second bind would fail. This is a deterministic negative that
does not need a network interface to exist, unlike probing the machine's LAN
address, which would skip on a CI runner and skipping reads as passing.

**A2. A busy port is fatal.** Occupy 8300, start `jura-trace-api`, assert a
non-zero exit and assert stderr contains the port number. This test fails
against today's code by construction:
`src-tauri/src/api/mod.rs:152-161` logs a warning and `return Ok(())` when the
bind fails, and `:150` logs "API server listening on http://{addr}" before the
bind is attempted. The test is the specification for changing that.

**A3. The sidecar really ran.** After a verify against a JPEG fixture, assert
`degraded == false` **and** that `detectorsRun` contains `ela`, `noise` and
`deepfake`, which only the sidecar can produce, **and** that the count is at
least ten in `deep` mode. A degraded run fails this test. A run that produced
five Rust-only detectors fails it. This is the floor that
`scripts/smoke_test_frozen_sidecar.py:289-307` did not have when it printed
"PASSED: all N mapped endpoints" for endpoints it never probed.

**A4. The guard self-test.** A fixture sidecar that answers `/health/ready`
with 200 and every `/forensics` route with 503, and a CI wrapper that fails
the job if A3 **passes** against it. This is BL-SILENT-001 plan item 2 applied
to the assertion that matters most here, and it is the only way to know that
A3 can fail.

**A5. Every exit code, from the real binary.** One case per code in the
section 7 table, invoking the built `jura` as a subprocess and asserting the
exact integer. Including: a low-trust fixture exits 0 with no `--fail-on`, and
20 with `--fail-on untrusted`. Including: a degraded response exits 0, and 8
with `--require-complete`. Shell assertions capture output to a variable and
check the command's own status before inspecting it, per Cause D.

**A6. The documentation matches the wire.** Parse the field names out of the
JSON examples in `docs/API_WRAPPER.md`, and assert every one of them exists in
a real response. This turns the twenty-row table in section 2.5 into something
that cannot silently re-open. The floor: assert the parser found more than
thirty field names, so a change to the document's formatting that makes the
parser extract nothing cannot pass as a clean run.

**A7. The Swagger page reaches nothing.** Fetch `/swagger-ui/` and assert two
things, not one. That the body contains no `http://` or `https://` URL whose
host is not the local server. **And** that every asset it references returns
200 from the local server. The first half alone would pass on an empty page.

**A8. Determinism.** Verify the same fixture twice and assert the two JSON
bodies are byte-identical except for `provenance.timestampUtc`.
`docs/API_WRAPPER.md:679` has promised this since May and nothing tests it.

**Where they run.** A1, A2, A5, A6, A7 and A8 need no sidecar and belong in
`src-tauri/tests/` and `cli/tests/`, inside the existing `ci.yml` Rust job. A3
and A4 need the frozen sidecar and belong with
`scripts/smoke_test_frozen_sidecar.py`, on the release path and on the weekly
schedule that BL-SILENT-001 plan item 1 asks for.

**The installed product.** `.github/workflows/installer-test.yml:139-190`
already launches the installed binary and polls
`http://127.0.0.1:8300/api/v1/health` on Linux, with the Windows equivalent at
`:378`. It is the only automated probe of the shipped REST API and it is the
right place to add the CLI: install the app, install `jura`, run `jura verify`
against a fixture, assert exit 0 and assert the reported `engineVersion`
matches the tag. That closes part of BL-TEST-001 for this surface rather than
adding another test of a build output.

**One rule from Cause C.** The version assertion runs against the installed
artefact, after signing and after packaging, not against `target/release`.
A gate must run on the bytes that ship.

## 12. Defects found while reading

Recorded, not fixed, per the constraint on this deliverable.

1. **The API server reports success when it did nothing.**
   `src-tauri/src/api/mod.rs:152-161`: when the bind fails, it logs a warning
   and returns `Ok(())`. The caller at `src-tauri/src/lib.rs:4675` only logs on
   `Err`, so a second instance of the app, or anything else holding 8300,
   produces an app with no API and no error. BL-SILENT-001 class, Cause B.

2. **The "listening" log line precedes the bind.**
   `src-tauri/src/api/mod.rs:150` logs "API server listening on http://{addr}"
   before `:152` attempts to bind. On failure the log reads as a success
   followed by a warning.

3. **The in-app text about the REST API is false.**
   `ui/src/routes/settings/+page.svelte:2935` tells the user "there is no
   programmatic key-authenticated REST endpoint yet". There is; it is running
   on 8300 as they read the sentence, and the comment eighteen lines above at
   `:2913-2918` says so.

4. **Community users cannot obtain the key their own server requires.**
   `ui/src/lib/featureFlags.ts:53` sets `V1_SHOW_API_KEYS = false`, hiding the
   whole panel, and `grep LicenceTier src-tauri/src/api/` returns nothing, so
   the server is not tier gated. A bootstrap key is created at
   `src-tauri/src/lib.rs:4654` and only its first eight characters are logged.

5. **The exit-code contract is documented twice and disagrees with itself.**
   `docs/API_WRAPPER.md:687-695` and `:1031-1039`. Code 5 is HTTP 422 in one
   and HTTP 400 in the other; code 6 includes degraded responses in one and not
   the other.

6. **`utoipa-swagger-ui` is a compiled, unused dependency**
   (`src-tauri/Cargo.toml:116`; no reference under `src-tauri/src/`), while
   the page it exists to serve loads unpinned assets from `unpkg.com`
   (`src-tauri/src/api/mod.rs:278`, `:282`). Already tracked as SR-24,
   JTV-209 and audit NEW-LOW-2, but the wasted dependency is not.

7. **The trust band exists only in the frontend.**
   `ui/src/lib/types.ts:1196-1200` and
   `ui/src/lib/components/VerdictSummary.svelte:20-27`. Nothing in Rust, in
   the API, in the PDF path or in the database knows what band a score falls
   into, so every consumer must re-implement it.

8. **Five Rust sidecar client methods target routes that no longer exist.**
   `src-tauri/src/sidecar.rs` still posts to `/forensics/video/metadata`,
   `/forensics/audio/metadata`, `/forensics/video/deepfake`,
   `/forensics/transcribe` and `/forensics/audio/deepfake`; the routes were
   removed under JTV-138 (`sidecar/app/api/forensics.py:555-562`). They are
   currently unreachable because feature groups gate them off, so this is dead
   code that would 404 if a gate were ever flipped.

9. **No `busy_timeout` on the SQLite connection.** `src-tauri/src/db.rs:34`
   sets `journal_mode=WAL` and nothing sets a busy timeout. Harmless with one
   process; reachable the moment a headless binary shares the file.

10. **`sidecar/app/config.py:13-14` declares `JURA_SIDECAR_PORT` and
    `JURA_SIDECAR_LOG_LEVEL` that nothing reads.** The argv defaults in
    `sidecar/main.py:212-216` are what actually bind. Setting the environment
    variable has no effect and gives no warning.

11. **`sidecar/app/config.py:35-37` and `sidecar/main.py:17` both still say an
    empty key means the sidecar "accepts all requests".** Since 21 May it
    returns 503 (`sidecar/main.py:174-178`).

12. **The only test of the empty-key path passes because of JTV-205.**
    `sidecar/tests/test_api_auth.py::test_no_auth_when_key_not_configured`
    asserts a non-401 with an empty key, which is true only under the
    `PYTEST_CURRENT_TEST` bypass at `sidecar/main.py:168-172`. Nothing asserts
    the 503 that a real caller gets.

13. **Three environment variable names for one thing.**
    `scripts/agents/config.py:14` uses `JURA_API_URL`,
    `scripts/build-sample-pack.sh:33` uses `JURA_API`, and
    `docs/c2pa-conformance/evidence-bundle/README.md:224` uses `JURA_API_KEY`.

Not a defect, but worth recording for anyone starting this work: a fresh
worktree cannot `cargo check` at all until `src-tauri/sidecar-bundle` and
`ui/build` exist, because `src-tauri/tauri.conf.json:55` globs
`sidecar-bundle/**/*` and `.gitignore:215` excludes it, and
`tauri::generate_context!` requires `frontendDist`. Both failures are build
script or proc macro errors with no obvious connection to the missing
artefacts. This is the same shape as BL-SILENT-001's defect 2.

## 13. Open questions

Three things this document decides without enough evidence, and what would
settle each.

**Q1. Does `jura-trace-api` ship only inside the desktop bundle?** Section 4
says yes and section 9 puts a Linux server tarball in the ten-day version.
Someone deploying to a headless Linux box does not want a webview and a Dock
icon in the payload. What would settle it: build the binary with the `api`
feature and no Tauri linkage and measure the artefact, and ask two or three
maintainers of the OSINT toolkits this work is aimed at what they would
package. If the webview-free binary plus the sidecar is meaningfully smaller
than the installer, the tarball moves into the five-day version.

**Q2. Should the desktop keep starting the API automatically?** It does today,
unconditionally, on a fixed port
(`src-tauri/src/lib.rs:4675`), for every tier, with the key panel hidden. Once
a headless binary exists, the two contend for 8300. Leaving it on is
convenient and is an always-listening local service the user did not ask for;
turning it off by default breaks `scripts/agents/`, the sample-pack script and
the C2PA evidence-bundle script, all of which assume 8300 is answering. What
would settle it: a decision on whether an always-on authenticated local
listener is consistent with the claim BL-CLAIM-001 is rewriting, taken with
legal review rather than inferred here. In the meantime this design leaves the
desktop behaviour unchanged and makes the headless binary fail loudly on the
collision.

**Q3. Should `--format text` or `--format json` be the default?** Section 8
chooses text on the grounds that a person running `jura verify photo.jpg` for
the first time should see something readable, and that the alternative is TTY
sniffing, which is worse than either. But the audience is scripts, and every
example in a toolkit listing would carry `--format json`. What would settle
it: watch what the first ten external users type. Cheaply approximated by
writing the quickstart both ways and seeing which one reads better, which is
a stage 5 task and can flip the default before anything is published.

**Deliverable**: W37-1.
**Written**: 10 September 2026.
**Status**: Design only. No production file is changed by this document.
**Scope**: the two v1.2.0 packaging changes a user feels directly. The
Windows cold start, and the download size.

Everything asserted about the current state below names a file and a line,

is no Windows machine in this session. Every measurement in this document

first, because it is half a day and it gates everything else, then the

## 1. How the macOS onedir arrangement works

This is the thing being ported, so it is worth stating exactly, rather
than as "the JTV-184 fix".

### 1.1 The spec file has two build modes behind one environment variable

`sidecar/jura-sidecar.spec` ends in an `if/else` on
`JURA_SIDECAR_ONEDIR`. With the variable set to `1` it builds an `EXE`
block with `exclude_binaries=True` and follows it with a `COLLECT` block;
otherwise it builds a single `EXE` carrying `a.binaries` and `a.datas`
inline. The comment above that branch records the measured effect, cold
launch dropping from about 90 seconds to about 5, and it also records the
two costs: the bundle grows because `COLLECT` does not compress, and the
signing surface grows from one Mach-O to hundreds of nested files.

`exclude_binaries=True` is the load-bearing flag. It tells the PyInstaller
bootloader to look for its payload in a sibling `_internal/` directory
rather than to self-extract.

### 1.2 The launcher stub exists because the payload cannot sit beside the executable

Tauri's `externalBin` entry in `src-tauri/tauri.conf.json:50-52` is
`binaries/jura-sidecar`. At bundle time Tauri places the matching file at
`Contents/MacOS/jura-sidecar`. The PyInstaller bootloader resolves
`_internal/` relative to its own executable, and Tauri offers no way to
put a directory tree into `Contents/MacOS/`. The tree therefore ships as a
Tauri resource, declared at `tauri.conf.json:53-56` as
`sidecar-bundle/**/*`, and lands at
`Contents/Resources/sidecar-bundle/`.

So the file Tauri spawns and the file that must run are in different
places. `src-tauri/sidecar-launcher/jura-sidecar-launcher.c` closes that
gap. It resolves its own path with `_NSGetExecutablePath`, walks to
`../Resources/sidecar-bundle/jura-sidecar`, refuses loudly with exit code
127 if that is missing, and otherwise `execv`s it with argv and the
environment passed through unchanged.

### 1.3 Why it is compiled and not a shell script

This is the part most likely to be mis-ported, so it is worth quoting the
reason rather than paraphrasing it. From the header of
`jura-sidecar-launcher.c`:

> Until 9 September 2026 this was a 38-line shell script. A script's code
> signature lives in extended attributes, not in the file. The DMG is a
> filesystem image and carries them, so the DMG passed every check. The
> updater archive is a tar, Tauri's tar writer drops extended attributes,
> and the client-side updater extracts with the same library, so the
> launcher arrived on a user's Mac "not signed at all" and Gatekeeper
> assessed the updated app as "rejected, no usable signature". A Mach-O
> binary carries its signature inside the file, which survives the
> archive.

The tracked binary at
`src-tauri/binaries/jura-sidecar-aarch64-apple-darwin` is 34,144 bytes.
`scripts/build-local-mac.sh:230` recompiles the launcher from source on
every build and proves the tracked file is that source compiled, using
`scripts/macho-equal.py`, which masks the linker's random `LC_UUID` and
requires every other byte to match. It never overwrites the tracked file.

### 1.4 How the bundle is staged and signed

`.github/workflows/release.yml:578` sets
`JURA_SIDECAR_ONEDIR` to `1` only when
`matrix.target == 'aarch64-apple-darwin'`.
`release.yml:594-607` copies `sidecar/dist/jura-sidecar/.` into
`src-tauri/sidecar-bundle/` and asserts both that the bootloader is
present and executable and that `_internal/` exists.

Signing then runs in a fixed order, because the order is the fix:

| Step | Where | What it does |
|---|---|---|
| Build app only | `release.yml:859-869` | `tauri-action` with `--bundles app`. No DMG, no notarisation |
| Per-file sign nested | `release.yml:958-991` | `codesign` every `.so` and `.dylib` deepest first, then the bootloader, then re-seal the `.app` |
| Verify nested | `release.yml:1002` | spot-check that nested code carries `TeamIdentifier=Y82C4P9L7F` |
| Regenerate DMG and updater | later in the same job | `cargo tauri bundle` from the re-signed `.app` |
| Notarise and staple | last | `notarytool` then `stapler` |

The local script mirrors it. `scripts/build-local-mac.sh` runs Phase 0.4
(launcher equality), Phase 0.5 (sign the staged source tree before the
bundler ever copies from it), Phase 1 (`--bundles app`), Phase 5a
(per-file sign inside the `.app`), Phase 5b and 5c (verify), Phase 6
(regenerate), Phase 6.5 (verify the updater archive), Phase 7 (sign the
DMG) and Phase 8 (notarise).

### 1.5 The phase that asserts the arrangement is correct, and what it learned

Phase 6.5 at `scripts/build-local-mac.sh:440-509` is the gate worth
copying, because of how it was wrong twice.

It was written after rc.29 to catch mis-signed nested binaries before
notarisation. As originally written it scanned
`$APP_PATH/Contents/Resources/sidecar-bundle`, but Phase 6 removes that
`.app` once it has packaged it, so `find` ran against a missing directory
with stderr silenced and the gate printed "All 0 nested Mach-O binaries in
final .app signed". It now extracts the updater archive to a temporary
directory, scans the `.app` inside it, and carries two floors: it dies if
`checked -eq 0`, and it compares the bundled `CFBundleShortVersionString`
against `tauri.conf.json`. It also judges `codesign --verify` by exit
status rather than by whether anything was printed, because the first
rewrite read `--verbose` success output as failure and refused a good
build.

Those three properties, scan the artefact that ships, refuse to pass on an
empty set, and judge by exit status rather than by output, are the
template for the Windows gates in section 5.

## 2. Change one: the Windows cold start

### 2.1 What the Windows build does today

`release.yml:578` is the whole of it:

```yaml
JURA_SIDECAR_ONEDIR: ${{ matrix.target == 'aarch64-apple-darwin' && '1' || '0' }}
```

Windows therefore takes the `else` branch of `jura-sidecar.spec` and
produces one self-extracting executable. `release.yml:618-623` copies
`sidecar\dist\jura-sidecar.exe` to
`src-tauri\binaries\jura-sidecar-x86_64-pc-windows-msvc.exe`, overwriting
the tracked 126-byte text placeholder whose entire content is
"PLACEHOLDER - replace with PyInstaller binary for production Windows
build". `release.yml:634-641` then creates
`src-tauri/sidecar-bundle/.keep`, a zero-byte file that exists only so
Tauri's strict resource glob has something to match, and ships inside the
MSI as a harmless artefact. `release.yml:750-765` Authenticode-signs the
sidecar executable with Azure Trusted Signing before Tauri packages it.

The consequence is written down in the repository. `CHANGELOG.md:316`
records the diagnosis that PyInstaller `--onefile` is fundamentally
incompatible with a Tauri sidecar, that the bootloader extracts the whole
payload to a fresh temporary directory on every cold launch, and that this
takes 90 to 200 seconds on a first run after install or after cache
eviction. `src-tauri/src/startup.rs:258-320` carries the same fact from
the other side: `cleanup_stale_mei_dirs` exists because those extraction
directories survive any unclean exit, and a live audit on 16 May 2026
found 22 of them totalling 3.5 GB on one developer machine.

Windows is where this matters. Live download counts, taken today from the
GitHub API for the v1.0.0 release, are the evidence for the share:

| Asset | Downloads |
|---|---|
| JuraTrace-1.0.0-Windows-x64.msi | 93 |
| JuraTrace-1.0.0-Windows-x64-setup.exe | 28 |
| JuraTrace-1.0.0-macOS-AppleSilicon.dmg | 42 |
| JuraTrace-1.0.0-Linux-x86_64.deb | 27 |
| Windows share of the 190 installer downloads | 63.7 per cent |

That corroborates the 64 per cent in `docs/release/v1.1.0-plan.md:215`
with a live number rather than a remembered one. The snapshot CSV the
repository provides for this,
`scripts/snapshot-download-counts.sh` writing to
`~/jura-trace-analytics/download-counts.csv`, holds a single row set from
18 June 2026 with almost every count at zero, so it does not support the
figure on its own.

### 2.2 The proposed change

Six edits, in this order. They are all in the release workflow, the spec
is already dual-mode, and the resources glob already ships a directory
tree.

**1. Turn the mode on for Windows.** `release.yml:578` becomes a
condition that is true for `aarch64-apple-darwin` and
`x86_64-pc-windows-msvc`. Linux stays on `--onefile` for now, and that
should be a deliberate line in the diff rather than a side effect, because
the Linux AppImage bundler already builds three full staging copies of the
payload and an uncompressed tree makes that worse.

**2. Add a Windows launcher.** A new
`src-tauri/sidecar-launcher/jura-sidecar-launcher-win.c`, or a
`#ifdef _WIN32` arm in the existing file. Its job is the same: resolve its
own directory, walk to `resources\sidecar-bundle\jura-sidecar.exe`, refuse
loudly if it is missing, and run it with argv and the environment passed
through.

The relative path differs from macOS. On macOS the launcher is at
`Contents/MacOS/` and the tree at `Contents/Resources/`, so the hop is
`/../Resources/sidecar-bundle/`. On Windows the application executable and
the sidecar sit in the install root and Tauri resources sit under a
`resources\` subdirectory of it, so the hop is
`resources\sidecar-bundle\`. This is an inferred conclusion, see 2.5.

**3. It cannot be `execv`, and it cannot be a script.** Two Windows
specifics, both of which change the launcher's shape rather than its
purpose.

The POSIX `execv` semantics the macOS launcher relies on, replacing the
process image so the PID Tauri holds is the bootloader's, do not exist on
Windows. The CRT's `_execv` creates a new process and terminates the
caller, so Tauri's `CommandChild` would be left holding a handle to a
process that has exited while the real sidecar runs on unparented. The
launcher must instead `CreateProcess` the bootloader with its standard
handles inherited, wait on it, and exit with its exit code, and it should
create a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and assign
the child to it so that killing the launcher kills the bootloader.

`src-tauri/src/startup.rs:345-420` is why the handles matter:
`spawn_sidecar` reads the child's stdout and stderr through Tauri's
`CommandEvent` stream and logs every line, and sets `PYTHONUNBUFFERED=1`
specifically so startup progress is visible in real time. A launcher that
does not inherit and forward those handles would silently remove the only
startup diagnostics the product has.

The launcher also cannot be a `.cmd` or `.bat`. Tauri's `externalBin`
resolution appends `.exe` for the Windows target, and, separately, there
is no Authenticode format for a batch file, so a script could never
satisfy the signing step. That is a different reason from the macOS one,
which was extended attributes lost through the updater tar, but it points
the same way.

**4. Build the launcher in CI rather than committing it.** The macOS
launcher is committed and proved byte-equal by `scripts/macho-equal.py`,
which works because the only nondeterminism Apple's linker introduces is a
random `LC_UUID` that the script masks. Reproducing an MSVC-built PE
byte-for-byte is a larger problem, and the Windows placeholder is already
overwritten in CI today, so the honest port is to compile the launcher on
the Windows runner and keep the tracked placeholder for `cargo check` and
`cargo tauri dev`. That gives up the macOS guarantee that the shipped
launcher is the committed source, so it needs its own assertion, see 5.1.

**5. Stage the tree and stop creating the placeholder.** The macOS copy
step at `release.yml:594-607` becomes shared with Windows, in PowerShell
for the Windows leg, with the same two assertions: the bootloader exists
and `_internal\` exists. The
`Create empty sidecar-bundle placeholder (Windows + Linux)` step at
`release.yml:634-641` narrows to Linux only. If it does not, it will drop
a `.keep` into a directory that now has real content, which is harmless
but obscures whether the copy ran.

**6. Sign the tree before Tauri packages it, never after.** The existing
Azure Trusted Signing step for the sidecar,
`release.yml:750-765`, points at `files-folder: src-tauri/binaries` with
`files-folder-filter: exe` and `files-folder-depth: 1`. Under onedir the
thing to sign is the staged tree, so a second invocation is needed against
`src-tauri/sidecar-bundle` with a filter covering `dll` and `pyd` as well
as `exe`, and a depth large enough for the deepest nested native library.
It must run before `cargo tauri bundle`, because once the payload is
compressed into an MSI or an NSIS executable the individual files are no
longer reachable by a folder scan. Section 4.1 is about what happens when
that order is got wrong, and section 2.4 is about what it costs, which is
one signing-quota unit per file and therefore not free to repeat.

**0. Before any of the above, answer the MSI question.** Section 2.4
records a documented WiX limit that this tree exceeds. Answering it costs
one unsigned Windows build and it decides whether steps 1 to 6 are the
whole job or the first half of a different one. It is numbered zero
because it comes first.

### 2.3 What the Windows tree will look like

There is no Windows onedir tree to measure, so this is projected from the
macOS one with the packages that only exist on the build host removed. The
method is in 3.3; the arithmetic is:

| Measure | macOS v1.1.0 as installed | Projected Windows, host-only packages removed |
|---|---|---|
| Files under sidecar-bundle | 3,348 | 2,645 |
| Native libraries (`.so` / `.dylib` on macOS, `.pyd` / `.dll` on Windows) | 613 | 520 |
| Uncompressed size, MiB | 700.5 | 442.1 |

Those two counts are the input to everything in 2.4. The file count is
what the installers have to carry and what the updater has to replace. The
native-library count is what has to be signed, once per release, at one
signing-quota unit each.

### 2.4 What does not port cleanly

Three sources are mixed below and they are kept apart deliberately.
Anything marked **repo** is measured or read here. Anything marked
**documented** is from Microsoft or Tauri documentation or from Tauri's
own source, and is a fact about the tooling that has not been verified
against this build. Anything marked **inferred** is reasoning. Section 2.5
lists everything that is not **repo**.

**Code signing, and it is not optional after all.** On macOS, signing
every nested binary is forced: `CHANGELOG.md:366` records that Tauri's
`--deep` pass leaves all 610 nested files ad-hoc signed and that hardened
runtime library validation then refuses `dlopen` on them at first launch,
which is exactly the "Analysis Engine offline" symptom the work exists to
remove.

Windows has no default equivalent of library validation, so the naive
reading is that unsigned nested libraries are a reputation problem rather
than a functional one. That reading is wrong for one population. Smart App
Control evaluates binaries as it loads them and blocks unknown unsigned
code, and Microsoft publishes a support page for exactly this case,
"Smart App Control has blocked part of this app", describing a trusted
application whose functionality partly fails because a file it opened
could not be judged safe (documented). Smart App Control is on only on
clean Windows 11 installs of build 22572 or later, is region-limited, and
turns itself off on machines it identifies as developer or enterprise, so
the affected population is a subset of new consumer machines rather than
all of Windows. It is still the population least equipped to diagnose a
half-working application.

There is a second, independent reason, and it is the one that argues the
change is worth making even setting the cold start aside.
`release.yml:747-749` already records that Defender frequently quarantines
unsigned PyInstaller binaries. Microsoft's own performance guidance names
unsigned binaries as the first cause of Defender CPU load, because
launching an unsigned binary starts a real-time content scan, and states
that highly reputable signed content shifts from a content scan to a
signature validation (documented). Signing the tree therefore converts
several hundred full content scans per launch into several hundred
signature checks.

**Signing has a per-file cost, and it is a quota rather than a rate.**
This is the finding most likely to change the shape of the work. Azure
Trusted Signing counts one signature per file, and the published quotas
are 5,000 signatures a month on the Basic tier and 100,000 on Premium
(documented). At 520 nested libraries plus the launcher and the two
installers, one Windows release run costs roughly 525 signatures.

| Tier | Monthly signatures | Windows release runs a month at 525 each |
|---|---|---|
| Basic | 5,000 | 9 |
| Premium | 100,000 | 190 |

Nine runs a month is enough for a release but not for iterating on one.
Three or four proving runs during development plus a release cut is
already half the month. `installer-test.yml` and `updater-e2e.yml` sign
nothing, so they do not add to it. Which tier this account is on is not
visible from the repository, and it is the first thing to check before
starting the work. No per-minute throttling figure is documented, and each
file is a separate round trip to the service, so the wall-clock cost of
the signing step is also unknown. The action's own timeout defaults to 300
seconds, which may not be enough for 520 files.

One further note on the action. `release.yml:750` and `release.yml:1338`
pin `azure/trusted-signing-action` at v0.5.0. That repository has since
been renamed to `Azure/artifact-signing-action` and its current major
version is 2 (documented). The pin still resolves, and this design does
not require changing it, but a step that signs 520 files rather than one
is the wrong moment to discover the action has moved on. Check whether the
pinned version supports the `batch-size` input before relying on it.

**The MSI has a documented structural limit and this tree exceeds it.**
This is the most concrete blocker found anywhere in this design.

`src-tauri/tauri.conf.json:81-87` configures NSIS and configures no WiX
options at all, so the MSI is Tauri's default. Tauri's bundler emits one
WiX `Component` per resource file, each with its own GUID, and references
every one of them from a single feature named `MainProgram` (documented,
from `tauri-bundler`'s `render_wix`). Microsoft documents a maximum of
1,600 components per feature. The projected tree is 2,645 files, which is
roughly 1.65 times the documented limit inside the one feature Tauri puts
everything in.

What that produces in practice is not established. It could be a WiX ICE
warning, a `light.exe` failure, or a package that builds and misbehaves at
install time. Nothing in this repository has built such a package, and no
Tauri issue was found acknowledging the limit, so it has to be settled
empirically before the design is committed to rather than after. It is
also the cheapest thing to test: one `cargo tauri build --bundles msi` on
a Windows runner with the tree staged, which needs no signing and
therefore consumes no quota.

If the MSI cannot carry the tree there are three routes, in increasing
order of disruption. Split the resources across additional WiX features
through a custom `main.wxs` template, which Tauri supports. Ship the tree
as a single archive inside the MSI and expand it in an install hook, which
reintroduces a first-run extraction and defeats the purpose. Or drop the
MSI for Windows, which is a decision that already has a place to be made:
`docs/release/v1.1.0-checkpoint-2026-09-10.md` lists "The NSIS versus MSI
question" as unsettled, and `release.yml:1780` currently makes the MSI the
updater target for `windows-x86_64`.

**The NSIS installer has a documented precedent and an upstream
mitigation.** Tauri's NSIS bundler writes a `File` directive per file and
a `CreateDirectory` per directory (documented). Tauri pull request 8233
was filed over a project with more than 200 folders and more than 1,000
files in `resources`, where the installer took about eight minutes to
build and install for 20 MB of content, and the fix brought it to about
ten seconds (documented). The pathology is known and already mitigated
upstream, and this tree is roughly two and a half times larger than the
one in that report. NSIS is the more likely of the two installers to
survive the change.

**Defender on a directory versus on a single file.** The intuition that
one large file is cheaper to scan than many small ones is the wrong way
round according to Microsoft's own guidance, which recommends extracting
containers precisely because parallel scanning is not possible inside them
(documented). Combined with the signed-content fast path above, a signed
onedir tree should be cheaper for Defender than an unsigned
self-extracting executable, at install and on every launch. No per-file
overhead figure is published, so this is a direction rather than a number,
and Microsoft's sanctioned way to get a number is
`New-MpPerformanceRecording` followed by `Get-MpPerformanceReport`, which
can be run inside the installer test.

**Path length.** The deepest relative path in the macOS tree is 135
characters (repo):

```
resources\sidecar-bundle\_internal\onnxruntime\tools\ort_format_model\ort_flatbuffers_py\fbs\RuntimeOptimizationRecordContainerEntry.py
```

That is a Python source file inside `onnxruntime`, so it is
platform-independent and will be present in the Windows tree too.
Prefixed with the install root:

| Install root | Full path length |
|---|---|
| `C:\Program Files\Jura Trace`, the MSI | 163 |
| `C:\Users\runneradmin\AppData\Local\Jura Trace`, NSIS on the CI runner | 181 |
| `C:\Users\alexandra\AppData\Local\Jura Trace`, NSIS with a nine-character user name | 179 |

The classic limit is 260 and it still applies. Long-path support on
Windows 11 is opt-in and needs two things, a machine-wide registry value
and a `longPathAware` element in the application manifest, and Tauri's
stock NSIS stub leaves `ManifestLongPathAware` unset (documented). A
per-user install cannot set machine policy, so 260 is the limit that
binds. There is roughly 79 characters of headroom against an ordinary user
name, which is comfortable but finite: a deeper Python package added
later, or an unusually long account name, eats it. Worth an assertion, see
5.1.

Note the asymmetry the same research turned up. Tauri's MSI has no
per-user mode at all, its `main.wxs` hardcodes the Program Files
directory, while NSIS with `installMode: currentUser` installs to
`$LOCALAPPDATA\Jura Trace` (documented). That matches what
`backlog/BL-TEST-001-nothing-tests-the-installed-product.md` observed on 7
September, where an MSI installed on its own landed in
`C:\Program Files\Jura Trace`.

**The updater, where the two installers diverge sharply.** Today an update
replaces one sidecar executable. After this change it must replace a tree
of 2,645 files, and the interesting case is the files that disappear
rather than the files that change.

Tauri's updater runs the NSIS installer with `/UPDATE`, and Tauri's
`installer.nsi` carries the comment "In update mode, always proceeds
without uninstalling" (documented). An NSIS update therefore overwrites in
place and removes nothing. Any file present in the old install and absent
from the new one stays on disk indefinitely, and the NSIS uninstaller
deletes from a generated file list and then calls a non-recursive `RMDir`,
so a later uninstall does not sweep them up either. The MSI path is clean:
Tauri's `main.wxs` emits a `MajorUpgrade` scheduled after
`InstallInitialize`, so `RemoveExistingProducts` removes the entire old
product before the new files install.

For a tree of this size that is a correctness hazard rather than disk
bloat. A stale `.pyd` or a stale module from the previous version sitting
beside the new `_internal` can be imported and misbehave, and the result
is an installation unique to the sequence of updates that produced it. It
is the class of fault this repository keeps finding: not a failure, a
wrong answer produced quietly.

That gives the NSIS versus MSI question a new input. The MSI is
structurally the safer updater target and may be the one that cannot carry
the tree. NSIS is the more likely to build and the one that leaves
orphans. Settle the MSI component question first, because it determines
which half of that trade is even available.

| The MSI exceeds the documented 1,600 components per feature | Documented limit, documented Tauri behaviour, untested combination | One `cargo tauri build --bundles msi` with the tree staged. No signing needed |
| NSIS handles the tree, slowly at worst | Documented precedent in Tauri pull request 8233 | The same build with `--bundles nsis` |
| An NSIS update leaves orphaned files and an MSI upgrade does not | Documented in Tauri's `installer.nsi` and `main.wxs` | The updater end-to-end workflow, extended per 5.1 |
| Installed paths stay under 260 characters | Repo measurement of the macOS tree, arithmetic for the Windows prefix | Assert it in the installer test |
| The projected Windows tree is 2,645 files and 442.1 MiB | Repo measurement of the macOS tree, minus packages absent from `sidecar/requirements-ci.txt` | Build it |

The honest summary is that this change has one documented structural
blocker to clear before anything else, the MSI component limit; one
documented cost that constrains how often it can be iterated, the signing
quota; and one documented correctness hazard, NSIS update orphans. None of
the three was visible from the repository alone, and all three are cheaper
to learn now than after a release.

### 3.2 The CLIP text encoder

`backlog/BL-SIZE-001-242mb-of-download-computes-10kb-of-constants.md` is
the specification and it is correct on its central point.
`sidecar/app/services/clip_detector.py:66-72` defines five literal
prompts, and `_encode_text_prompts()` at `:323-346` runs the text encoder
over them once and caches a `(5, 512)` float32 array. Saved as a `.npy`
that array is 10,368 bytes on disk, which was measured by calling
`numpy.save` on a `(5, 512)` float32 zero array and taking the length of
the buffer. The 10,240 figure in the backlog is the raw array; the extra
128 bytes are the `.npy` header.

The two files that exist to produce it total 255,094,140 bytes, which is
**243.3 MiB**. That comes out of every platform's download, because
`src-tauri/tauri.conf.json:53-56` ships `models/*` on all of them.

The change is larger than "delete two files", and the reason is at
`clip_detector.py:219-229`:

```python
    vision_path = os.path.join(models_dir, "clip-vit-b32-vision.onnx")
    text_path = os.path.join(models_dir, "clip-vit-b32-text.onnx")

    if not os.path.exists(vision_path) or not os.path.exists(text_path):
        logger.warning(...)
        return False
```

`_ensure_model()` requires **both** files and returns `False` if either is
missing. Ship without the text encoder and without changing this function
and CLIP detection does not fail: it becomes unavailable, quietly, through
a warning log, and every verdict is then computed from fewer detectors.
Section 4.2 is about that.

The full edit is therefore:

1. Generate `models/clip_text_prompt_embeddings.npy` from the canonical
   `models/clip-vit-b32-text.onnx` with a new script, alongside
   `scripts/export_clip_onnx.py`, and commit it. At 10,368 bytes it
   belongs in git, unlike the ONNX weights, and committing it is what lets
   Windows and Linux CI build without downloading the encoder at all.
2. Change `_ensure_model()` to require only the vision encoder, and to
   stop creating `_text_session`.
3. Change `_encode_text_prompts()` to populate `_text_prompt_cache` from
   the `.npy`. The call site already caches, so nothing downstream moves.
4. Clear the same globals in `unload_clip_model()` at
   `clip_detector.py:113-118`, which currently nils `_text_session` too.
5. Drop the two text files from `release.yml:707-736`, which downloads
   four ONNX assets by pattern and verifies them, and from
   `scripts/onnx-model-sha256.manifest`, which pins all four SHA-256s. Add
   a pin for the `.npy` in the same manifest.
6. Keep the text encoder in the canonical `models/` directory and in
   `scripts/export_clip_onnx.py`, so the array can be regenerated if the
   prompts change. Record in the model card that it was generated at build
   time and from which file.

`src-tauri/tauri.conf.json` needs no edit: the resources entry is a glob,
and BL-REL-001's resolution note records that the explicit enumeration was
considered on 9 September 2026 and deliberately not taken.

### 3.3 pyarrow, and a correction to the backlog and the plan

The backlog records pyarrow at 114 MB as "a transitive dependency that
does not appear in `sidecar/requirements.txt` at all". Both halves of that
are right, and both understate what is going on.

**It is bigger than 114 MB.** `du -sk` over every arrow-family entry at
the top of `_internal` gives:

| Entry | MiB |
|---|---|
| `pyarrow` | 113.7 |
| `libarrow.2300.dylib` | 41.2 |
| `libarrow_flight.2300.dylib` | 19.2 |

PyInstaller hoists a package's bundled shared libraries to the top of
`_internal`, so counting only the `pyarrow/` directory misses two thirds
of it. The version on the dylibs, 2300, matches the installed
`pyarrow 23.0.1`.

**It arrives with company.** The same import chain brings `pandas` at 21
MiB, `grpc` at 18 MiB, `tokenizers` at 7.9 MiB and `hf_xet` at 6.8 MiB.
Arrow family plus those four is **258.4 MiB**.

**It is not in the Windows or Linux payload.** This is the finding that
changes the plan's arithmetic. `sidecar/jura-sidecar.spec` contains:

```python
for _optional_pkg in ["chromadb", "sentence_transformers"]:
    try:
        d, b, h = collect_all(_optional_pkg)
        datas += d; binaries += b; hiddenimports += h
    except Exception:
        pass
```

That `try` succeeds or fails according to what happens to be installed on
the machine running PyInstaller. On this machine it succeeds: `python3 -c
"import chromadb"` reports 0.5.23 and `sentence_transformers` reports
3.4.1, both from
`/opt/homebrew/Caskroom/miniconda/base/lib/python3.13/site-packages`, and
`import pyarrow` reports 23.0.1 from the same prefix. `datasets` 4.8.3 is
installed too, and its own metadata declares `pyarrow>=21.0.0`, which is
the chain.

macOS releases are built from that environment.
`scripts/build-local-mac.sh:190` runs PyInstaller with the host Python,
and `docs/release/mac-release-runbook.md` is the record that macOS ships
locally.

Windows and Linux do not. `release.yml:537-551` installs
`sidecar/requirements-ci.txt` on a clean runner. Resolving that file's
full transitive closure gives 49 packages and pyarrow is not one of them:

```
python3 -m pip install --dry-run --ignore-installed \
    --report /tmp/w37-ci-resolve.json -r sidecar/requirements-ci.txt
```

pyarrow, chromadb, sentence-transformers, pandas, grpcio, tokenizers and
datasets are all absent from the resolved set. `sidecar/requirements.lock`
agrees: it is the pip-compile output of `requirements.txt` and `grep`
finds none of those names in its 1,206 lines. So on a CI runner the
`try/except` catches an `ImportError`, and the whole 258.4 MiB was never
there.

Two consequences.

**The size claim needs restating by platform.** `docs/release/v1.1.0-plan.md:193`
promises "roughly 356 MB off a 1.15 GB payload". The 1.15 GB is the macOS
uncompressed payload and the 356 MB is 242 plus 114, both decimal
megabytes, both macOS. Restated honestly:

| Platform | CLIP text precompute | pyarrow and friends | Total off the uncompressed payload |
|---|---|---|---|
| Windows | 243.3 MiB | 0 | 243.3 MiB |
| Linux | 243.3 MiB | 0 | 243.3 MiB |
| macOS | 243.3 MiB | 258.4 MiB | 501.7 MiB |

The compressed download shrinks by less than that, because ONNX weights
compress poorly and Python trees compress well. The macOS DMG should fall
furthest.

**The pyarrow half is not really a size change.** It is a build-hygiene
change: two `collect_all` calls make the shipped bundle a function of what
is installed on the build machine, which is the same class of fault as
BL-DEPS-004, where the version CI tests and the version that ships are
guaranteed to differ. The fix is to delete the opportunistic block from
the spec, or to add `pyarrow`, `pandas`, `chromadb`, `sentence_transformers`
and `datasets` to the existing `excludes` list at
`jura-sidecar.spec` and let the loop fail closed. Deleting the block is
cleaner: nothing in `sidecar/app/` imports either package, and the
comment above it says it exists so CI builds without them do not abort,
which the `excludes` list achieves without the host coupling.

Doing it makes the macOS bundle match the Windows and Linux ones, which is
worth more than the 258 MiB, because it means a macOS build can no longer
ship code that CI never tested.

### 3.4 What breaks if either is wrong

**If the precomputed array is wrong.** A `(5, 512)` float32 array of the
wrong numbers is indistinguishable, at every layer of the product, from
one of the right numbers. The zero-shot bars in Expert View move, and the
verdict thresholds documented at `clip_detector.py:81-95` were calibrated
against the current weights.

The backlog's own caution is the right one: the arrays should be
bit-identical because it is the same model, tokeniser and deterministic
inference, but onnxruntime versions differ across platforms and the host
runs a different version from CI. `scripts/validate_clip_onnx_drift.py`
and `docs/calibration/univfd-v9-onnx-validation.md`, which gated the FP32
ONNX port at mean cosine similarity 1.000000 and maximum drift 0.000163,
are the precedent for how that gets demonstrated rather than assumed.

**If the encoder is dropped without the code change.** Covered above and
in 4.2. The product keeps working and the number changes.

**If pyarrow removal takes something with it.** Nothing under
`sidecar/app/` imports pyarrow, pandas, chromadb or sentence_transformers;
`grep` over the tree finds no import of any of them. The risk is not a
missing import, it is that the same edit removes the `collect_all` for
`chromadb`, whose transitive collection may be supplying a hidden import
some other package needs on the macOS build only. That is precisely why
the verification in 5.2 is a real verification run and not a green build.

## 4. Risk

`docs/release/v1.1.0-plan.md:194-195` says that touching model packaging
in the days before a freeze is how releases break, and the repository's
own history is the argument. Both risks below are stated in the shape of
the rc.29 failure, because both are that failure.

### 4.0 The rc.29 shape, restated

From `CHANGELOG.md:195`: the build script's Phase 5a per-file signed every
Mach-O inside the staged bundle correctly, and then Phase 6's
`cargo tauri bundle` re-copied from the source directory into the `.app`,
overwriting the signed files with unsigned ones. The `.app`'s top-level
re-seal baked hashes of unsigned nested files into the new signature. The
DMG passed `codesign --verify` locally and Apple's notarisation rejected
it, naming 600 files. Recovery cost 30 minutes of manual work on release
day.

Three properties made it possible. A later step mutated the artefact after
the step that made it correct. The local check ran on something other than
the bytes that shipped. And the only gate that would have caught it lived
outside the build, at Apple.

### 4.1 The Windows onedir equivalent

**The failure mode.** The signing step signs the staged tree at
`src-tauri/sidecar-bundle`, and `cargo tauri bundle` then packs a copy
into the MSI and the NSIS executable. If any step between those two
regenerates or re-copies the tree, or if the signing is placed after the
bundle for symmetry with the installer-signing step at
`release.yml:1336-1352`, the installers ship 520 unsigned native libraries
inside a correctly signed installer.

**Why it is worse than rc.29.** On macOS the same mistake is caught,
eventually, by notarisation, which is an external party that inspects
every nested binary and says no. Windows has no such gate. An installer
whose entire payload is unsigned installs cleanly, launches, and passes
every assertion in `installer-test.yml` today, and it also passes on the
CI runner specifically, because a GitHub-hosted `windows-latest` image is
not a clean consumer machine with Smart App Control enforcing. The
consequence appears on user machines instead: Defender quarantines, and,
for the Smart App Control population in 2.4, an application where part of
the functionality does not work and the rest does. Weeks later, spread
across people who do not file bugs. That is the exact shape BL-SILENT-001
is about, a mechanism reporting success while doing nothing, with the
added twist that the environment where it is tested is the environment
least able to detect it.

**The assertion that catches it.** After the installers are built and
Azure-signed, and after the installer test has performed a real install,
walk the installed tree and require that every PE inside it carries a
valid Authenticode signature from the expected subject. In PowerShell that
is `Get-AuthenticodeSignature` over
`resources\sidecar-bundle` filtered to `.exe`, `.dll` and `.pyd`, with
three floors borrowed from `build-local-mac.sh` Phase 6.5:

- Fail if the number of files checked is zero. An empty scan is not a
  pass. This is the fault Phase 6.5 shipped with for three months.
- Fail if the number checked is below a floor of a few hundred, because a
  scan that found four files has found the wrong directory.
- Judge each file by the `Status` property, not by whether anything was
  printed, and fail the step on the first `NotSigned` or `UnknownError`
  rather than counting warnings.

It must run on the installed tree, not on the staging directory, because
the staging directory is not what shipped.

For the Smart App Control half, the same assertion is not enough, because
the runner does not enforce it. Microsoft publishes an audit policy for
exactly this, which logs what would have been blocked without blocking it,
and writes CodeIntegrity Operational events 3076 for evaluation and 3077
for enforcement (documented, see 2.5). Applying that policy on the test
runner and asserting zero 3076 events after a launch would turn an
untestable population into a testable one. That is a larger piece of work
than the signature scan and it is a candidate rather than a requirement,
but it is the only way found to observe the Smart App Control outcome from
CI rather than from a user's report.

**The second-order risk, and its assertion.** The launcher is now built in
CI rather than committed and byte-compared, so the guarantee that the
shipped launcher is the reviewed source is gone. Replace it with two
cheap assertions: the file placed at
`src-tauri\binaries\jura-sidecar-x86_64-pc-windows-msvc.exe` must not be
the 126-byte tracked placeholder, and it must begin with the `MZ` PE
magic. Both are one line each and both catch a copy step that silently did
not run.

### 4.2 The size-change equivalent

**The failure mode.** Remove `clip-vit-b32-text.onnx` from the bundle
without changing `_ensure_model()`, or change `_ensure_model()` and get
the `.npy` path wrong, and `clip_detector.py:222` returns `False`. The
sidecar starts. The health endpoint answers. Verification runs. The CLIP
and UnivFD detector reports unavailable, the composite is computed from
what remains, and the number the product exists to produce is different
from the number it produced last release. The only trace is one
`logger.warning` line.

That is the same instinct BL-SILENT-001 catalogues at
`sidecar/app/services/deepfake.py:255`, where a bare `except` around
`joblib.load` returned `None` and the caller fell back to a heuristic
score, so a disabled classifier was visible only as a shift in the verdict
distribution. It took a dependency drift test to find it.

**Why a green build does not catch it.** The Python suite runs against
modules, not against a bundle. `scripts/smoke_test_frozen_sidecar.py:289-307`
skips any capability reporting false and then prints
"PASSED: all N mapped endpoints" where N is the size of the mapping rather
than the number probed, so a sidecar reporting `clip_detect: false` passes
it. BL-SILENT-001 lists that as instance 5 of its ranked table.

**The assertion that catches it.** Two, and both are needed.

- **Availability, asserted rather than printed.** The bundled sidecar's
  `/health` must report `clip_detect` true, and the smoke test must fail
  on a false capability rather than skipping it. This is a small fix to
  `smoke_test_frozen_sidecar.py` that BL-SILENT-001 already wants for its
  own reasons, and the size change is the occasion.
- **Equality of the array itself.** A test that loads
  `models/clip_text_prompt_embeddings.npy`, runs the text encoder over
  `_TEXT_PROMPTS` when the encoder is present, and requires the two to be
  bit-identical, reporting mean cosine similarity and maximum absolute
  drift the way `docs/calibration/univfd-v9-onnx-validation.md` does. It
  runs on macOS locally and on any CI leg where the encoder is available.
  On legs where it is not, the SHA-256 pin in
  `scripts/onnx-model-sha256.manifest` is what stands in for it.

Neither of those proves the verdict is unchanged. That needs section 5.2.

## 5. How each is verified

`backlog/BL-SILENT-001-mechanisms-that-report-success-while-doing-nothing.md`
is the design constraint for this section. Its Cause B is that success was
defined as "the step exited 0" rather than "the expected artefact exists
and is valid"; its Cause C is that a gate must run on the bytes that ship,
last, after every mutation; its Cause D is that exit status comes first
and output second. Every assertion below is written against those.

### 5.1 The Windows change: started quickly, not started at all

**What the existing test asserts, and what it does not.**
`.github/workflows/installer-test.yml:367-392` installs the real
installers on `windows-latest`, launches the installed executable, and
polls `http://127.0.0.1:8300/api/v1/health` once a second for 60 seconds.
It then asserts `status -eq "ok"` and that `version` matches the tag, and
it prints `sidecar available : $($health.sidecarAvailable)`.

`src-tauri/src/api/routes.rs:64-82` shows what those assertions are worth
for this purpose. `status` is the literal string `"ok"`, returned
unconditionally. `version` is `env!("CARGO_PKG_VERSION")`, compiled in.
`sidecar_available` is the only field in the response that reflects
anything about the sidecar, and it is printed and never asserted.

So the current Windows test passes while the sidecar is still extracting,
and would pass if the sidecar never started at all. It does not
distinguish "started quickly" from "started at all" because it does not
currently assert either.

**The structural assertion, which timing cannot fake.** The decisive proof
that onedir is in effect is not a stopwatch, it is the absence of an
extraction. `src-tauri/src/startup.rs:258-262` states the mechanism: the
`--onefile` bootloader extracts to `$TMPDIR/_MEIxxxxxx` on every cold
launch. After launching the installed app on the runner, assert that no
`_MEI*` directory appeared under `$env:TEMP`, and that
`resources\sidecar-bundle\_internal` exists in the install tree with more
than a floor of files in it. Those two together cannot be satisfied by a
fast runner, a warm cache or a lucky ordering. They are true only if the
shape changed.

**The timing assertion, with both ends closed.** Then measure. Record the
wall-clock time from `Start-Process` to the first `/api/v1/health` response
carrying `sidecarAvailable: true`, and fail on three conditions with three
different messages:

| Condition | Message |
|---|---|
| The loop completed without ever observing `sidecarAvailable: true` | The sidecar did not start. This is not a slow start |
| It became true, but later than the budget | The sidecar started, and took N seconds against a budget of B |
| The loop ran zero iterations, or the executable path was empty | The measurement did not happen. Not a pass |

The third row is the BL-SILENT floor and it is the one most often left
out.

Run the measurement twice, on the first launch after install and again
after the process is stopped and relaunched. Under `--onefile` both are
slow, because the extraction repeats. Under `--onedir` the first is
moderate and the second is fast. Recording both makes the change visible
as a shape rather than as a single number, and it protects against a
budget that a warm runner happens to satisfy.

**Set the budget from a measurement, not from a guess.** Run the timing
step against the current `--onefile` v1.1.0 installers first, on the same
runner class, and record what it says. That number is the before. The
repository has no Windows timing at all today, so this run is worth doing
even if the port slips.

`src-tauri/src/lib.rs:4364` is a second, cheaper source for the same
figure: the readiness probe already logs
`Sidecar ready after N poll attempt(s) (elapsed Ns)`. Uploading the app
log as a test artefact gives a value from inside the product to compare
against the value measured from outside it, and a disagreement between
them is itself informative.

**The signing assertion.** As set out in 4.1, on the installed tree, with
a floor.

**The path-length assertion.** One line, and it belongs beside the signing
scan because it walks the same tree. Measure the longest full path under
the install root and fail above a threshold set below 260 with margin, say
240. Section 2.4 measures the current worst case at 181 characters on the
CI runner's account name, so this passes today and exists to catch a
future package that is nested more deeply than `onnxruntime`. Report the
longest path in the pass message, so the headroom is visible rather than
implied.

**The Defender measurement, optional but cheap.** Microsoft's sanctioned
way to get a number is `New-MpPerformanceRecording` around the install and
the first launch, then `Get-MpPerformanceReport -TopFiles 20`. It does not
need an assertion. Uploading the report as an artefact for the before and
after runs turns a claim about scanning cost into two files somebody can
compare.

**The updater assertion.** `.github/workflows/updater-e2e.yml` already
installs a previous version on `windows-latest`, points it at a staging
manifest and reads the client's verdict through the WebView2 DevTools
protocol, per the 10 September update in
`backlog/BL-TEST-001-nothing-tests-the-installed-product.md`. Extend it by
one step: after the update applies, assert the installed
`resources\sidecar-bundle\_internal` contains no file that was present in
the previous version's tree and absent from the new one. That is the
orphan case from 2.4, and it is the one that produces a mixed tree rather
than a clean failure.

### 5.2 The size change: prove the removed weight was not load-bearing

A green build proves nothing here, and neither does a passing unit test,
because the failure mode in 4.2 is a product that works and answers
differently.

**The assertion is a real verification run producing the same result as
before.** Concretely:

1. **Capture the baseline before touching anything.** Take a fixed set of
   images, the sample pack from `scripts/build-sample-pack.sh` plus a
   sample of the calibration corpus, and run each through the current
   installed v1.1.0 product's `/api/v1/verify`
   (`src-tauri/src/api/routes.rs`). Store the full scored response per
   image, not just the verdict. Commit the baseline, or store it beside
   the calibration notes in `docs/calibration/`, with the version and the
   date it was taken.
2. **Re-run after the change, against the built product, not the source
   tree.** The comparison must be made against an installed build with the
   text encoder absent, because that is the configuration whose behaviour
   is in question.
3. **Require equality where equality is claimed.** The verdict and the
   `verdict_level` must be identical for every image. The CLIP and UnivFD
   score must be identical, or must differ by less than a stated tolerance
   with the tolerance justified in the same way
   `docs/calibration/univfd-v10onnx-divergence-fix.md` justifies its own.
   The zero-shot five-bar readout must be identical, since it is the only
   consumer of the precomputed array.
4. **Refuse to pass on an empty run.** If the comparison examined zero
   images, or if any image failed to produce a response, the run fails.
   The report must state how many images were compared, and that count
   must be asserted against an expected number rather than printed.
5. **Assert `clip_detect` is true in the same run.** Otherwise steps 1 to
   4 can be satisfied by a build where the detector is uniformly
   unavailable in both the baseline and the comparison.

Point 5 is not hypothetical caution. It is the difference between proving
the weight was not load-bearing and proving that removing it changed
nothing because nothing was running in either case.

**For the pyarrow half, the same run on macOS.** The pyarrow removal only
affects macOS, so its proof is a local `scripts/build-local-mac.sh` build
with the `collect_all` block gone, `scripts/smoke_test_frozen_sidecar.py`
green with capability assertions rather than skips, and the same
golden-verdict comparison against the same baseline. If the macOS numbers
match the Windows numbers after both changes, which they should because
they will finally be built from the same package set, that is a stronger
result than either comparison alone.

## 6. Effort, and whether they can ship separately

### 6.1 Estimates

| Change | Estimate | The low end assumes | The high end is reached if |
|---|---|---|---|
| The MSI feasibility probe | 0.5 day | One unsigned `cargo tauri build` on a Windows runner with the tree staged, reading whether WiX accepts 2,645 components in one feature | It needs the staging half of the port built first to have a tree to test with, which is most of a day rather than half |
| Windows onedir, if the MSI carries the tree | 2 to 4 days | The port is mechanical. The spec is already dual-mode, the resources glob already ships a tree, the macOS signing sequence is a template, and the launcher is a small C program | Signing is slow or overruns the action's 300-second timeout; the NSIS install time regresses the way Tauri pull request 8233 describes; the updater leaves orphans. Each costs a Windows CI run to learn, and the signed ones cost quota as well as minutes |
| Windows onedir, if it does not | add 2 to 4 days | A custom `main.wxs` splitting resources across several WiX features is the smallest of the three routes in 2.4 | The answer is to drop the MSI, which is not an engineering task. It is the unsettled NSIS versus MSI decision, it changes the updater target at `release.yml:1780`, and it needs a call from Paul rather than a commit |
| CLIP text precompute | 1 to 1.5 days | The code change is five small edits plus a 10,368-byte file, `_encode_text_prompts` becomes a file read, and the equality check has a precedent in `scripts/validate_clip_onnx_drift.py` | The cross-platform equality check finds drift on one platform, which forces the backlog's fallback of shipping the encoder for that platform only, plus the recalibration argument that goes with it |
| pyarrow removal | 0.5 to 1 day | Deleting nine lines from the spec and rebuilding | Removing the `chromadb` collection turns out to have been supplying a hidden import something else needed on macOS, which surfaces only in a full local build and smoke test |

`docs/release/v1.1.0-plan.md:215` estimates the Windows port at about two
days and `:193` estimates the size pair at about one. Those are the low
ends here, and they are defensible low ends: the code really is small.
The difference is that this document counts what it costs to find out
whether the code is right.

There is no Windows machine. Every Windows unknown resolves only in CI,
`backlog/BL-TEST-001-nothing-tests-the-installed-product.md` records that
a full Windows release build costs 144 charged minutes, and section 2.4
adds a second currency: on the Basic signing tier there are about nine
signed Windows runs a month in total, shared with actual releases. Two or
three round trips is most of a day of wall clock even when the code is
right, and it is not free.

### 6.2 Independence

They are independent. They touch different files, they fail in different
places, and neither depends on the other landing.

| | Windows onedir | Size work |
|---|---|---|
| Spec file | the mode toggle | the `collect_all` block and `excludes` |
| Release workflow | the sidecar build, staging, signing and placeholder steps | the ONNX download and verify step |
| Sidecar Python | none | `clip_detector.py` |
| Rust | none | none |
| Tauri config | none | none |

The only real coupling is that both change what a Windows installer
contains, so shipping them in one branch means one Windows proving run
instead of two. That is a false economy: a failure in a combined run is
ambiguous between a signing problem and a model-availability problem, and
distinguishing them costs another run anyway. Separate branches, separate
proving runs.

There is one ordering benefit, and it points one way. The golden-verdict
baseline that section 5.2 requires is worth capturing once and using
twice. If the size work goes first, its baseline is taken against today's
Windows shape, and the onedir change afterwards reuses the same baseline
to show that changing the packaging did not change the answer. Taken in
the other order, the baseline has to be recaptured.

## 7. Ordering relative to the freeze

**Recommendation: run the MSI feasibility probe now, before the v1.2.0
window opens. Then land the size work, then the Windows port, both in the
first two weeks of the window. Neither lands in the week before the
v1.2.0 freeze.**

The reasoning, in order of weight.

**The MSI probe comes first and is not really release work.** It is half a
day, it needs no signing and therefore no quota, and its answer decides
whether the Windows port is a two-day port or an installer decision that
needs Paul. Running it before the window opens is the difference between
discovering that in week one and discovering it in week three. It is also
the only item here that can be run against `main` without a branch that
intends to ship, because it is a question rather than a change.

**The plan's own rule applies and should be honoured literally.**
`docs/release/v1.1.0-plan.md:193-195` says of this exact work: "Monday 21
September or not at all. Touching model packaging in the days before a
freeze is how releases break." The v1.1.0 freeze is Friday 25 September
(`:355`). That rule was written about a four-day margin. It is the right
rule and it generalises: the margin these changes need is measured in
proving runs, not in days of coding.

**Neither belongs in v1.1.0 now.** `docs/release/v1.1.0-checkpoint-2026-09-10.md:89`
records the Windows port as not started and `:92` records the size work as
not started, both against a release whose remaining scope the checkpoint
already describes as more than fits. Adding a change that can only be
validated in Windows CI to a release in its closing phase is the thing the
rule exists to prevent.

**Size first, for three reasons.** It is smaller and mostly provable on
this machine. It establishes the golden-verdict baseline the onedir change
then reuses. And its risk is numerical rather than structural, so a
problem shows up as a diff against the baseline rather than as an
installer that misbehaves on a platform nobody here can run.

**Windows second, and early, because it is the one that needs calendar
time rather than working time.** Two to four days of effort spread across
however long two or three 144-minute CI runs take to schedule and read.
Starting it in week one of the window leaves room for the second and third
run. Starting it in week three does not, and the signing quota makes a
late scramble worse rather than better, because the runs that would be
needed to recover are the same runs the release cut needs.

**A hard line for the freeze week.** No change to `bundle.resources`, to
`jura-sidecar.spec`, to the signing sequence or to
`src-tauri/models/` inside the final week before the v1.2.0 freeze. If
either change is not proved by then, it goes to v1.3.0. rc.29 cost 30
minutes of manual recovery on a release day; the Windows equivalent has no
notarisation step to catch it, so it would cost a release instead.

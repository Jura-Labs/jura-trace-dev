# The deferred dependency work, planned for v1.2.0

**Written**: 10 September 2026, against `main` at `594f67bb`.
**Deliverable**: W37-1.
**Status**: Planning only. Nothing in this document has been merged, closed
or commented on. No manifest, lockfile or source file was changed to write
it.

On 8 September 2026 five sidecar bumps and the whole Dependabot queue were
deferred until after the v1.1.0 release. That release is out: `gh release
list --repo Jura-Labs/jura-trace` shows **Jura Trace v1.1.0, Latest,
published 2026-09-10T18:59:34Z**. The deferral has expired, so this is what
the work now looks like.

The organising claim is that "dependency work" is not one kind of work. A
patch bump to a test runner, a Rust crate that breaks compilation, a
numerical library that feeds a classifier and a re-serialised model artefact
are four different risks with four different kinds of evidence. Grouping
them by ecosystem, which is how Dependabot presents them and how
`backlog/BL-DEPS-001` first triaged them, hides that. This document groups
them by how the failure would show up.

## 2. The risk classes

Five classes. Every open item sits in exactly one, assigned by the risk that
determines what evidence the change needs, not by the first thing that goes
wrong. Two items break compilation and are still classed by their silent
half, because a compile error is free to discover and the silent half is
what costs.

| Class | The failure mode | How you find out | What it costs to be sure |
|---|---|---|---|
| **1. Loud in CI** | It does not compile, or a test fails | The pull request is red | Nothing beyond the fix. CI is the whole test |
| **2. Loud, but only outside CI** | It breaks a workflow no pull request runs | Nobody finds out until a release is attempted | A throwaway release dispatch |
| **3. Silent behaviour change** | It compiles, tests pass, and something a user meets behaves differently: a file routes to a different pipeline, a certificate stops validating, an update stops downloading | Only a named manual check, or a user report | A specific, written smoke test per item |
| **4. Silent numerical drift** | It compiles, tests pass, and a detector score moves | Only a before-and-after run against a fixed corpus | The drift harness, section 6 |
| **5. Shipped-artefact change** | The bytes a user downloads change, and the published accuracy figures are claims about those bytes | Only by proving the new artefact reproduces the old one's outputs | Everything in class 4, plus a hash and provenance trail |

The line that runs through the whole of this is class 1 against classes 3
and 4. `backlog/BL-DEPS-004` is the repository's own statement of it: a green
check on a sidecar bump was a statement about the version CI installed, not
the version the release would ship. The guard that now catches that
(`scripts/check_requirements_sync.py`, merged in #36) turned a silent
divergence into a red build. It did not, and could not, make any test in the
suite sensitive to a moved number. Both halves are still true.

### 3.5 Two gaps in the guard, found while checking it

Both are new to this document.

**A `>=` floor above the locked version passes the guard.**
`scripts/check_requirements_sync.py` compares `==` pins only, by design.
Pull request #12 proposes `pytest-asyncio>=1.4.0` in
`sidecar/requirements.txt`, while `sidecar/requirements.lock:565` pins
`pytest-asyncio==1.3.0`. The floor is not satisfiable against the lock, the
guard is silent, and `ci.yml` installs 1.3.0. That is precisely the
BL-DEPS-004 failure in the one shape the guard cannot see. It is harmless
here because pytest-asyncio is test-only, and it would not be harmless on a
runtime package.

**There is a fourth sidecar manifest and nothing reads it.**
`sidecar/requirements-build.txt` pins `torch==2.10.0`,
`torchvision==0.25.0` and `open-clip-torch==3.3.0`. Pull requests #43 and #6
change it and nothing else. `grep -rn "requirements-build" .github/ scripts/
AGENTS.md docs/` returns nothing, and the file's own header says "NEVER
install this in CI or production". So it cannot break a release, and it is
also the file that pins the versions
`scripts/export_clip_onnx.py`, `scripts/train_univfd_probe.py` and
`scripts/validate_clip_onnx_drift.py` run under. Bumping torch there does not
ship anything; it changes the environment that would regenerate the ONNX
model if anyone ever re-exported it. That is a reproducibility question, not
a release question, and it should be recorded as one.

## 6. Group C. Silent behaviour change

**Class 3.** These compile, the tests pass, and something a user meets
behaves differently. Each one needs a named check, written down, because no
automated test in this repository covers any of them.

### 6.1 reqwest 0.12.28 to 0.13.2, #25

The compile break is two call sites and both are trivial:
`RequestBuilder::query` on the blocking builder, at `src/sidecar.rs:1455`
(watermark embed) and `:1652` (claim check). Both talk to
`http://127.0.0.1`, so no TLS is involved at either.

The real change is the TLS backend, and the repository's TLS situation is
more layered than the brief describes. Verified with `cargo tree`:

| Path | Crate | Trust roots | Consumers |
|---|---|---|---|
| Updater | reqwest 0.13.2 via `tauri-plugin-updater` 2.10.0 | `rustls-platform-verifier` 0.6.2, so the operating system trust store | The update check and download |
| c2pa's own HTTP | reqwest 0.12.28 with feature `rustls-tls-webpki-roots`, plus `ureq` 3.4.1 | `webpki-roots`, a compiled-in Mozilla root set | Certificate and timestamp fetches under `c2pa` 0.90.20 |
| The application's own clients | reqwest 0.12.28 with default features, so `default-tls` | `native-tls` 0.2.14, the platform TLS stack | `src/ris.rs:550` to `vision.googleapis.com` and `api.tineye.com`, `src/lib.rs:1216` to the weather API, `src/lib.rs:1724` for the download-by-URL verify path |

`cargo tree -e features -i reqwest@0.12.28` shows the `rustls-tls` feature
arriving through `c2pa v0.90.20 -> c2pa feature "default"`, and `cargo tree
-i native-tls` shows `native-tls` arriving through the same reqwest 0.12.28
that `jura-trace` depends on directly. Both backends are compiled in today,
and the application's builders select neither explicitly: `grep -rn
"use_native_tls\|use_rustls\|add_root_certificate\|danger_accept" src-tauri/src/`
returns nothing.

reqwest 0.13's dependency list in `Cargo.lock` has no `native-tls`, no
`hyper-tls` and no `tokio-native-tls`; it has `rustls-platform-verifier`.
So merging #25 moves the application's own outbound HTTPS from the platform
TLS stack to rustls with the platform verifier. It does not unify the tree,
because c2pa pins 0.12 and both versions are already present.

**What breaks if this is wrong**: reverse image search stops working behind
a corporate TLS-inspecting proxy, or on a machine whose only trust anchor is
an enterprise root, or on an older Windows install. Silently, from the user's
side, as a network error.

**How you would know**: nothing in the test suite covers this. The named
check is: run a reverse image search against Google Vision with a real key,
on macOS and on Windows, and run one verify-from-URL against an HTTPS host,
before and after. If anyone has a machine with a TLS-inspecting proxy, that
is the case that decides it, because `rustls-platform-verifier` and
`native-tls` disagree exactly there.

**Estimate**: 1 day, mostly the two-platform check.

### 6.2 rcgen 0.13.2 to 0.14.10, #22

Six compile errors, and `CertificateParams::from_ca_cert_pem` no longer
existing is the significant one. This is the per-install local certificate
authority behind Sovereign-mode signing, which is the product's stated
differentiator. Certificates users have already signed against were issued
by the 0.13 code path.

**What breaks if this is wrong**: newly issued certificates differ from
existing ones in a way that makes previously signed assets fail to verify
against the local CA, or the CA is regenerated and every prior signature
orphaned.

**How you would know**: sign an image under 0.13, upgrade, and verify that
image again without regenerating the CA. Then sign a new one and verify it.
Then check the issued certificate's fields against one issued before.
Nothing automated does this today.

**Estimate**: 1.5 days. The API migration is the smaller half.

### 6.3 rusqlite 0.31.0 to 0.40.2, #19

Nine minor versions, and the break is one removal repeated: rusqlite no
longer implements `ToSql` and `FromSql` for `u64`. Every site is in
`src/db.rs`. The fix is mechanical (store as `i64`, or wrap), and it is
mechanical in a way that invites a silent bug, because a `u64` that does not
fit an `i64` changes value rather than failing.

The bundled SQLite moves too: `libsqlite3-sys` is 0.28.0 today.

**What breaks if this is wrong**: a timestamp or a size column reads back
wrong, or an existing database on a user's machine stops opening after an
update.

**How you would know**: the Rust suite (572 tests) will catch the
straightforward errors once it compiles. It will not catch a value
round-tripping wrong at the top of the `u64` range, and it will not catch a
migration problem on a database created by v1.1.0. The named check is: open
a v1.1.0 database file with the new build and read every table.

**Estimate**: 2 days.

### 6.4 infer 0.16.0 to 0.19.0, #18

File type sniffing is what routes a file to a pipeline. A sniffing change is
a routing change, and a routing change is a different set of detectors on
the verify page. Note that `infer` 0.19.0 is **already in the tree** via
`tauri-plugin-updater` and `tauri-utils` (`cargo tree -i infer@0.19.0`), so
this bump unifies a duplicate rather than introducing a new version.

**How you would know**: verify one file of each supported type and compare
the detector list before and after. Include an AVIF and a HEIC, because
those are where format handling has been wrong before.

**Estimate**: 0.5 days.

### 6.5 uvicorn 0.34.0 to 0.52.4, #8, and pydantic 2.11.3 to 2.13.5, #7

Eighteen minors of the ASGI server that the sidecar runs under
(`sidecar/main.py:218`), and two minors of the model layer every response
passes through. The sidecar test suite covers the API surface, so most of
this is loud. The part that is not loud is startup: `JTV-142` was a sidecar
startup hang and it was a v1.0 blocker.

**How you would know**: the Python job covers the request paths. Startup
needs the installed product, on each platform, which is `BL-TEST-001`
territory and does not exist yet. Minimum viable check: launch the built
application and confirm the analysis engine comes up, on macOS and Windows.

**Estimate**: 1 day for both, dominated by the launch checks.

### 6.6 certifi 2026.2.25 to 2026.7.22, #11, and kamadak-exif 0.5.5 to 0.6.1, #27

certifi is a root store refresh for the Python side. It is close to
mandatory and close to zero risk; the only failure mode is a root being
withdrawn that something still depends on.

kamadak-exif is used in `src-tauri/src/metadata.rs`, including
`extract_gps_coord` at line 633, and GPS feeds the weather cross-check. A
parsing change would move a displayed field rather than a score.

**How you would know**: verify one photo with GPS EXIF and compare the
metadata panel before and after.

**Estimate**: 0.5 days for both.

## 7. Group D. Silent numerical drift

**Class 4.** This is where the product's published numbers live.

### 7.1 The combined numpy, scipy, opencv and pillow-avif bump

This one is already evidenced.
`docs/calibration/numerical-stack-drift-sep2026.md`, dated 8 September, is
84 golden images across five codecs, six environments and five probes, with
the single-package environments present specifically so that a difference in
the candidate can be attributed rather than argued about. Reading it
properly, which the brief asks for, it establishes four things.

**Which features drift, and by how much.** The whole of the measurable drift
is scipy, at a maximum absolute delta of 2.655e-4, on 16 feature indices: 0
to 8 and 55 to 58 (the FFT and DCT spectral features), plus 68, 73 and 79.
numpy's contribution is 7.3e-12, which is float accumulation noise eleven
orders of magnitude smaller. OpenCV's is 3.4e-6 and confined to indices 80,
82 and 83, which GBM v4 does not consume, because the vector is trimmed to
`n_features_in_ = 80` before prediction.

**Which library is responsible.** scipy, unambiguously, and only scipy.

**That the output did not move.** `predict_proba` on the candidate feature
vectors is bit-identical to `predict_proba` on the baseline vectors on all
84 images, with zero verdict flips at the sidecar's own thresholds and at
0.30, 0.50 and 0.70. UnivFD was bit-identical on everything including the
512-dimension ONNX embedding. Copy-move, NPR and GAN outputs were identical
on every image.

**One behaviour change that is not drift.** OpenCV 5 decodes AVIF, where
4.11 did not. `cv2.imdecode` failed on all 14 AVIF and all 14 HEIC images
under 4.11 and on only the 14 HEIC under 5.0. So the GAN fingerprint
detector produces a result on AVIF where it previously recorded an error,
and a user comparing an AVIF verdict before and after the release sees an
extra detector row. That is probably an improvement and it is definitely a
release note.

The document's own two qualifications should be carried forward rather than
dropped. "No split crossed on 84 images" is an observation, not a proof: a
gradient-boosted ensemble has discrete thresholds and an image sitting
within 2.7e-4 of one would flip. Three of the 84 sit within 0.01 of the
0.25 authentic threshold and the nearest is 0.0028 away, which is ten times
the drift, so the margin is real but it is a margin and not a guarantee.

**Recommendation: take all four together, in one pull request, with the lock
regenerated, and cite the existing calibration note.** No new drift run is
needed. The evidence is two days old at the time of writing and nothing in
the four proposed versions has changed since.

**Estimate**: 1 day, of which most is `pip-compile` and the release note
about AVIF.

### 7.2 onnxruntime 1.24.4 to 1.29.0, #44

**This is not covered by the drift test, and it should be.** Every one of
the six environments in `numerical-stack-drift-sep2026.md` held onnxruntime
at 1.24.4; the environment table says so explicitly. onnxruntime is what
runs the CLIP vision and text sessions
(`sidecar/app/services/clip_detector.py:233` and `:237`) that produce the
UnivFD embedding, and UnivFD v10onnx's published AUC-ROC of 0.9929 is a
claim about the numbers those sessions emit. Five minor versions of an
inference runtime can change kernel selection, fusion and float
accumulation.

**What breaks if this is wrong**: the UnivFD probe score moves, the ensemble
score moves, and a verdict flips, with nothing anywhere saying so.

**How you would know**: probe 4 of the existing harness, unchanged. It
already hashes the CLIP preprocessing array, the 512-dimension ONNX
embedding and the LogisticRegression probe score, and it already reported
`max abs delta 0.0` across all 512 dimensions between environments. Running
it with onnxruntime as the only variable is exactly the attribution design
the harness was built for.

**Estimate**: 0.5 days, given the harness exists. Section 8 is about whether
it does.

### 7.3 regex 2025.10.23 to 2026.9.3, #42

Not obvious, and worth stating carefully. `regex` is pinned in
`sidecar/requirements.txt:67` with a comment saying it is "required by
app/services/clip_tokenizer.py (imported as `import regex as re`)".
`sidecar/app/services/clip_tokenizer.py:30` imports it, `:113` compiles the
CLIP byte-pair-encoding pattern with it, and `:162` runs `re.findall` over
that pattern to tokenise. A change in that library's matching behaviour
changes the token sequence, which changes the text embedding, which changes
the zero-shot comparison.

Eleven months of releases. It is almost certainly fine and it is
categorically not a boring string library in this codebase.

**How you would know**: probe 4 again, and additionally hash the tokeniser's
output for a fixed prompt set before and after. That second part is ten
lines and does not exist yet.

**Estimate**: 0.5 days, run alongside 7.2.

### 7.4 anyio 4.12.1 to 4.15.1, #41

Genuinely boring, and included here only because the version guard makes it
look like the other two. It is a concurrency primitives library under
starlette. Class 1 in everything but its red check. Regenerate the lock and
merge.

**Estimate**: included in the lock work.

## 8. The drift harness: can it be rerun, and what does it cost

The calibration note says the probe scripts, environment build logs,
`golden_set.json`, both `pip freeze` outputs and the full `comparison.json`
are "in the session scratchpad at `~/.claude/jobs/de5265ce/tmp/drift/`, not
committed, since they depend on a corpus that is not in the repository".

Checked. **It is still there, and it is one deletion away from not being.**

| Component | State on 10 September |
|---|---|
| Probe scripts | Present. `probes/` holds `probe_common.py`, `probe1_decode.py` through `probe5_cv.py`, `golden_select.py`, `gen_variants.py`, `attrib.py`, `compare.py`, `run_all.sh`, `run_attrib.sh` |
| Golden set definition | Present. `golden_set.json`, 35,768 bytes, 84 paths with generation parameters, seed 20260908 |
| Results and comparison | Present. `results/` for all six environments plus `baseline_run2`, and `comparison.json` at 65,924 bytes |
| The six virtual environments | **Gone.** `envs/` no longer exists. The build logs reference it and the runner scripts call `$D/envs/$env/bin/python` |
| The corpus | Present. `/Volumes/Samsung USB` is mounted |

So a rerun needs the environments rebuilt, and the logs say what that costs.
`logs/build_baseline.log` and `build_candidate.log` both record `start` and
`install rc=0` thirteen and eleven seconds apart, using `uv`. The whole
8 September session ran from 22:36:23 (first environment build) to
22:56:02 (last attribution probe), which is **under twenty-one minutes wall
clock for six environments, golden-set generation, ten probe runs and nine
attribution runs**. A single-variable attribution run, which is what
onnxruntime and regex each need, is two environments and four probes:
call it **fifteen minutes**, plus the corpus being plugged in.

That is cheap enough that "we did not have time to check" is not an
argument. But two things stop it being a repeatable asset today.

**It is not committed.** It lives under `~/.claude/jobs/de5265ce/`, which is
a session scratchpad. Nothing prevents it being cleared.

**It is pinned to one machine and one checkout.** `probes/probe_common.py`
hardcodes `DRIFT = "/Users/paulgriffiths/.claude/jobs/de5265ce/tmp/drift"`
and `REPO = "/Users/paulgriffiths/Downloads/ecoadvisor/juralabs"`, then
inserts `<REPO>/sidecar` on `sys.path` and points `JURA_MODELS_DIR` at
`<REPO>/models`. It runs against the main checkout, not against a worktree,
so a rerun tests whatever `main` happens to be at that moment.

**Recommendation, and it is a small piece of work with a large payoff**:
commit the probes to `scripts/drift/`, replace the two hardcoded paths with
a repository root derived from the script location and a corpus root read
from an environment variable, and keep `golden_set.json` alongside them. The
corpus stays out of the repository; the method stops being one person's
scratch directory. The calibration note already says "the method above is
sufficient to rewrite the probes", which is true and is a worse position
than not having to.

**Estimate**: 1 day to commit and de-hardcode the harness. Count it once,
against the first numerical bump that uses it.

## 9. Group E. The shipped artefact: scikit-learn 1.9.0

**Class 5, and the only item in it.** This is the most consequential thing
in the queue and the recommendation is not to ship it in v1.2.0.

### 9.1 What is actually blocked

Under scikit-learn 1.9.0, `joblib.load` on `deepfake_classifier.joblib`
raises `ModuleNotFoundError: No module named '_loss'`. The file's bytes are
unchanged, so the SHA-256 gate passes and is not involved. The pickle
references a private scikit-learn module path that 1.9.0 has moved.

The silence half of that is now fixed. `sidecar/app/services/deepfake.py`
lines 265 to 296 replace the old bare `except Exception: _classifier = None`
with a `logger.exception` whose message names the scikit-learn version as
the thing to check, and whose comment cites the drift note. That landed in
#38. So a repeat of this failure would be a startup log line rather than a
statistical anomaly. It is still a failure.

### 9.2 What re-serialising actually touches

Four scikit-learn artefacts carry SHA-256 gates, not one:

| Artefact | Gate | Bundled? |
|---|---|---|
| `deepfake_classifier.joblib` | `deepfake.py:241`, `512def7e...ba14a` | Yes. `models/` and `src-tauri/models/`, byte-identical, confirmed with `shasum -a 256` |
| `univfd_probe.joblib` | `clip_detector.py:60`, `0534a9e8...6a86` | Yes, both directories, byte-identical |
| `audio_deepfake_stage1.joblib` | `audio_deepfake.py:50` | No. `models/` only, and the audio route is not exposed (`sidecar/app/api/forensics.py:59`) |
| `audio_deepfake_stage2.joblib` | `audio_deepfake.py:53` | No, same |

`src-tauri/tauri.conf.json:54` bundles `"models/*"` relative to `src-tauri/`,
so the shipped set is two files. A migration is therefore: two artefacts
re-serialised, four copies replaced, two constants edited, and two
non-shipped artefacts to decide about. The UnivFD probe loads under 1.9.0
today with an `InconsistentVersionWarning` and scores identically, so it is
the easier of the two and it should move at the same time rather than being
left to warn.

### 9.3 The numbers that are claims about these bytes

The product publishes accuracy figures, and they are in the shipped
application, not only in a document. `ui/src/routes/help/model-cards/+page.svelte`
gives AUC-ROC 0.9868 for GBM v4 at line 167 and 0.9933 at line 330;
`ui/src/routes/help/methodology/+page.svelte:706` states the whole claim in
one sentence: "a GradientBoosting classifier (GBM v4, trained on over 10,000
images from 14 generator families, cross-validation AUC-ROC 0.9868,
authentic false-positive rate 4.54%, calibrated threshold 0.49)" combined
with "the UnivFD v10onnx probe ... AUC-ROC 0.9929, authentic FP rate 3.87%,
recall 95.77%".

`docs/calibration/gbm-v5-v11-archive-jun2026.md` is where those came from
and it is also the precedent for how this project treats them. GBM v5 was
archived because AUC fell 0.9868 to 0.9755, false positives rose 4.54% to
6.11% and AI recall fell 92.52% to 88.88%, all three against written hard
gates. UnivFD v11 was archived for a HEIC legacy-format AUC miss of 0.42
percentage points on n=300, which that document itself notes is
statistically indistinguishable from sample noise, and the all-or-nothing
gate refused promotion anyway. That is the standard. A re-serialisation
should not be held to a lower one just because it is not a retrain.

Those figures are also outside the repository's control once used. The brief
records that they appear in a funding application. A number in a grant
application that describes a model artefact no longer shipped is a claims
problem of exactly the kind `backlog/BL-CLAIM-001` to `BL-CLAIM-003` exist
to prevent.

### 9.4 Recommendation

**Do not ship scikit-learn 1.9.0 in v1.2.0. Do the migration as a separate,
evidenced pull request, sequenced for the release after, and only if
something asks for it.**

The reasoning is that the benefit is currently zero and the risk is not.
`uvx pip-audit` reports no advisory against scikit-learn 1.8.0. Nothing in
the product needs a 1.9.0 feature. The entire case for the bump is that it
is newer. Against that: it changes the bytes users download, it invalidates
two hash constants, and it puts the published accuracy figures back in play.
That is a bad trade in a release the plan describes as small.

**What would have to be proven before it ships**, in this order:

1. The re-serialised estimator gives **bit-identical `predict_proba`** on the
   84-image golden set, against the current artefact's outputs. Not "within
   tolerance": identical. A re-pickle of the same fitted estimator should
   reproduce exactly, and anything less means something changed that was not
   supposed to.
2. **Zero verdict flips** at `AUTHENTIC_THRESHOLD` 0.25 and
   `SYNTHETIC_THRESHOLD` 0.58, and at 0.30, 0.50 and 0.70, which is the
   comparison the existing probe 3 already makes.
3. The same for `univfd_probe.joblib` through probe 4, including the
   512-dimension embedding and the probe score.
4. Both new SHA-256 values recorded, both constants updated, and all four
   file copies replaced. `shasum -a 256` on `models/` and `src-tauri/models/`
   must agree pairwise, as they do today.
5. A calibration note in `docs/calibration/` recording the above, in the
   shape `numerical-stack-drift-sep2026.md` and
   `pillow-12-decode-drift-sep2026.md` established.
6. An explicit statement, in that note, that the published AUC-ROC, false
   positive and recall figures are unchanged and why, or a list of every
   place they are stated and a plan to change them.

**The fallback if the re-serialised model does not reproduce the current
one's numbers**: stay on scikit-learn 1.8.0. That is not a defeat and it
should be written into the plan in advance, so that the person doing the
work is not deciding it under sunk cost.

Concretely, if step 1 fails, three options in order of preference. First,
pin scikit-learn 1.8.0 in all three manifests with a comment naming this
document, and add it to `.github/dependabot.yml`'s pip `ignore` for minors,
accepting that this also mutes 1.8.x security updates and recording that
trade explicitly (the existing comment at
`.github/dependabot.yml:112-148` explains why that side effect is
unavoidable). Second, retrain rather than re-serialise, which means the
full v5 gate machinery in `gbm-v5-v11-archive-jun2026.md` and a genuine
possibility of the same archive outcome. Third, and only if a security
advisory eventually forces 1.9.0, ship the re-serialised model with changed
numbers and change every published figure at the same time, which is a
release of its own.

The `.bak-1.7.2` file the drift note cites as evidence that this migration
has been done once before is no longer present (`ls src-tauri/models/`
shows two files), so that precedent exists in history rather than on disk.

**Estimate**: 2 to 3 days when it is done, of which about half is evidence
rather than code. Zero days in v1.2.0, because the recommendation is not to.

## 10. Recommended order

Cheap and loud first, and I agree with the principle, with one amendment.
The plain form of "cheap and loud first" would put the whole Dependabot
queue ahead of the numerical work. That is wrong here for one reason: the
drift harness is uncommitted and lives in a scratch directory. Committing it
is the thing that makes every later numerical decision cheap, and leaving it
until it is needed risks it not being there. So it goes second, before the
first bump that depends on it, not last.

One line per group.

| Order | Group | One line |
|---|---|---|
| 1 | Rebase the queue | Eight pull requests are red for a reason that has nothing to do with them, and the queue cannot be read honestly until that is cleared |
| 2 | Commit the drift harness | Fifteen minutes of rerun cost is worth nothing if the scripts are one `rm` from gone, and everything in groups D and E depends on them |
| 3 | Group A, class 1 | Merge what CI fully proves: #31 with the updater caveat, #20, #40, #12, #43, #6, and the non-major npm pair with the PDF render check |
| 4 | Group D.1, the four-package numerical bump | The evidence already exists, is two days old, and the only work is regenerating the lock and writing the AVIF release note |
| 5 | Group D.2 and D.3, onnxruntime and regex | One attribution run each on the harness from step 2, because both sit on the CLIP path and neither was covered by the September test |
| 6 | Group B, the release actions | Split #13, merge the three CI-covered actions, and rehearse `release.yml` on a throwaway tag before tauri-action 1.0.0 and trusted-signing 2.0.0 go anywhere near a real one |
| 7 | Group C, the silent-behaviour Rust bumps | #25, #22, #19, #18, #8, #7, #11, #27, each with its named check written down before the merge, not after |
| 8 | The vitest 4 decision | A decision, not a bump; timebox it and take it or drop the `ignore` entry deliberately |
| 9 | Group E, scikit-learn | Not in v1.2.0. See section 9 |

Steps 1 to 5 are the ones I would commit to for a small November release.
Steps 6 and 7 are the ones I would take if the release has room. Step 8 is a
decision that can be made in half an hour and then scheduled. Step 9 is
deferred again, on purpose and with a written reason this time rather than
by running out of week.

## 11. What I would not do at all

A bump with no benefit and real risk is a cost, not hygiene. Four here.

**scikit-learn 1.9.0, in v1.2.0.** Section 9. No advisory, no needed
feature, and it changes the shipped artefact and puts published figures back
in play.

**torch 2.10 to 2.14 and torchvision 0.25 to 0.29, #43 and #6.** These edit
`sidecar/requirements-build.txt`, which by its own header is "NEVER install
this in CI or production" and which `grep -rn "requirements-build" .github/
scripts/ AGENTS.md docs/` shows nothing reads. So the bump ships nothing and
tests nothing. It does change the environment that would regenerate the ONNX
CLIP model, and the current pins are the ones that produced the model in
production. Four minors of torch is exactly the kind of change that makes a
future re-export not reproduce.

The right action is the opposite of a bump: leave the pins, and add a line
to that file's header saying the torch pins are the ones the shipped ONNX
model was exported under and should move only alongside a re-export and a
`scripts/validate_clip_onnx_drift.py` run. Merging #43 and #6 quietly
removes information.

**`npm audit fix --force`.** BL-DEPS-002 already says this and it is worth
restating because the command is one keystroke from the one that is correct.
It pulls the vitest and vite majors in behind something that reads like a
routine fix.

**`@sveltejs/kit`, `@sveltejs/adapter-static` and `cookie`, the three lows.**
`npm audit` proposes `@sveltejs/kit@0.0.30` as the fix, which is a downgrade
across a major boundary from `^2.70.3` and is not a fix. There is no clean
resolution; the `cookie` advisory is about out-of-bounds characters in a
cookie name in a framework whose dev server is not shipped. Wait for
SvelteKit upstream. Do not let the number 10 in an audit summary drive an
action here.

One thing I would also not do, phrased as a warning rather than a refusal:
**do not reopen the five closed pull requests casually.** The comment at
`.github/dependabot.yml:112-148` records that closing a Dependabot pull
request stores an exact-version ignore condition, and that those conditions
apply to security updates too. If an advisory's minimum fixed version turned
out to be exactly 2.5.2, 1.18.1, 1.9.0, 5.0.0.93 or 1.6.0, the fix would be
muted until the closed pull request was reopened. Reopening #1, #4, #9 and
#10 as part of step 4 clears that, and is a reason to do step 4 rather than
let it slide.

- **The sidecar suite still asserts bounds.** The conditional assertions at

  nothing. That is `BL-TEST-002` work and it is the standing reason every
  class 4 item needs the harness rather than the test suite.
- **`BL-DEPS-004` options (a), (c) and (d) are still open.** In particular
  (c), whether Dependabot would regenerate a pip-compile lock if
  `requirements.lock` were renamed `requirements-lock.txt`, is unconfirmed,

  future sidecar bump. That is a half day that pays back repeatedly and it
  is not costed above because it is not dependency work.
- **The `>=` floor gap in the version guard** described in section 3.5 has
  no ticket. It is about thirty minutes of work in
  `scripts/check_requirements_sync.py` to compare a `>=` floor against the
  locked version and fail when the floor is higher.
- **Nothing here has been merged, closed or commented on.** The queue is as
  it was found.

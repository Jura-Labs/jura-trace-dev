## Why this release got bigger, and what the build actually costs

Paul's reasoning on 4 September: GitHub Actions minutes for the Windows and
Linux builds make frequent small releases uneconomic, so batch work into
fewer, larger releases and ship a minor update between them only when
security demands it.

The reasoning holds. The numbers refine it, and they point somewhere
slightly different from where you would expect. Measured from the actual
release runs on 19 June 2026:

| Job | Wall time | Multiplier | Charged minutes |
|---|---|---|---|
| Build, Windows x64 | 72 min | 2× (private repo) | **144** |
| Build, Linux x64, successful | 35 min | 1× | 35 |
| Publish, prepare, create | ~3 min | 1× | 3 |
| **A clean two-platform release** | | | **~180** |

macOS does not appear, because it is built locally. That is worth keeping,
since macOS runners bill at 10×.

The org is on a Team plan, which includes 3,000 Actions minutes a month for
private repositories. So **a clean release costs about six per cent of the
monthly allowance.** That is not nothing, but it is not the constraint it
feels like.

**The actual cost driver is failure, not frequency.** On 19 June there were
four failed runs, two runs cancelled after **120 minutes each** on the Linux
RPM compression hang, and two successes. The two cancelled Linux runs alone
burned 240 charged minutes, which is more than the entire successful
Windows build. One bad release day cost several times what a clean release
costs.

Three consequences follow, and they all point the same way as the existing
plan:

1. **Fixing CI is the cheapest cost saving available.** A release that
   succeeds first time is the whole saving. That is floor item F6 and the
   release gate, already scoped.
2. **BL-SIZE-001 pays twice.** Removing 356 MB from the payload cuts build,
   compression and upload time on every future run, not just the download.
   It moves from "conditional if there is slack" to straightforwardly
   worth doing.
3. **Batching is right, but two substantial releases beat one enormous
   one.** See the note on Q4-2 below.

Both caching layers already exist in `ci.yml` and `release.yml`, so the
72-minute Windows build is not a missing-cache problem. If build cost
becomes pressing beyond this, that job is where to look.

## How this satisfies Q4-2, resolved 4 September

Q4-2 measures "Trace release pipeline live and 1.0.x shipped" as **two

into one large release would have left a single release inside the quarter.

It also gives this release somewhere to shed scope without the date

## What this release is

v1.0.0 shipped on 18 June 2026 and nothing has been committed since 19
June. In that time nobody has received an update, because the updater has
never worked; nothing has been tested by CI, because it only runs on pull
requests and has been red since April; and nothing could have told us about
a new vulnerability, because all three detection routes are silent.

So this is a repair release. It is not a small one: with the accessibility
and honesty fixes it carries roughly fifteen user-visible changes, which is
why it is v1.1.0 and not v1.0.1. The single measure of success is that a
person running v1.0.0 receives it without being told to.

### Explicitly out, and why

**Watermarking stays out, and the extra time does not change that.** The
algorithm records 0% survival at JPEG Q70, crop 20%, resize 75% and
screenshot, which are precisely the transformations it exists to survive.
That is an operating envelope, not a schedule problem, so a longer release
window is not an argument for including it. It stays at v1.2.0, and if it
ships there it ships with the envelope stated plainly.

**Conformant signing stays out for the same kind of reason.** The blocker
is not time, it is an unresolved identity model: a shared Jura Labs
certificate makes every user's content say "signed by Jura Labs", and
per-user certificates are an onboarding and cost problem. That is a
decision for Paul, not a task, and it belongs with the Pro tier.

Also out, unchanged: ADJPEG, PRNU, SynthID (proprietary and not
implementable), model download-on-first-run, quantisation, Flathub, Snap
and an apt repo.

## The release gate

**The single non-negotiable: the live updater leg on real v1.0.0 installs,
macOS and Windows, before any announcement.** Everything else here has a
fallback. That one is the release's reason to exist.

### Automated, on the release commit, in CI and not merely locally

1. CI green on a pull request carrying the release diff, then the **same
   SHA** confirmed green on push-to-main once the trigger fix lands. That
   confirmation is itself the proof the CI repair worked.
2. `cargo test`, `clippy -D warnings`, `fmt --check`, run **both with and
   without** the new PDF feature, because a feature that only builds one way
   will rot.
3. The sidecar pytest suite, including new auth tests.
4. `svelte-check`, vitest, Playwright.
5. OSV producing **findings or an explicit clean SARIF**, verified by a
   nonzero package count in the run log rather than by the job being green.
6. A manifest contract test against the live worker: `signature` is
   minisign content and not a URL, `url` ends with the expected asset name
   per platform, the version parses, and the platform keys match what Tauri
   expects.

### Manual, in order

1. **Staging leg.** A throwaway local v1.0.x pointed at a staging manifest
   for v1.1.0. Confirms format, signature verification, install, relaunch.
2. **Live leg.** A pristine v1.0.0 install on production endpoints, left
   untouched, on macOS and Windows. After the real assets and manifest go
   live it must update unprompted. **Do not announce until both pass.**
3. The Verification Record Export: export, verify the signature with an
   independent tool, tamper one byte, confirm verification fails.
4. The Windows asset rename against the manifest URL, exactly. This rename
   is the likeliest way to re-break the updater we just fixed.
5. One full verify run per platform, as a sidecar auth smoke test.

### Regression couplings worth naming

- **`npm audit fix` reaches dompurify through jspdf**, which is the
  production PDF report path. Generate a report for a C2PA-signed image and
  for a deepfake-flagged one, and look at both. html2canvas is a jspdf peer
  and an audit fix that bumps it changes report screenshots.
- **The PDF cargo feature can drift the `c2pa` crate version**, which
  carries the Validator Conformant award. Diff `Cargo.lock` for c2pa, coset
  and x509 before and after. If c2pa-rs moved, re-run the conformance test
  vectors.
- **The startup update check races sidecar startup**, which has a hang
  history. Test with the network down, with `juralabs.org` black-holed so
  it hangs rather than refuses, and with a malformed manifest. It must not
  delay first paint.
- **`concurrency: ci-${{ github.ref }}`**: push and pull-request runs on the
  same SHA may cancel each other once the trigger changes.

### Proving the CI repair, rather than assuming it

On a scratch branch, break one thing per lane and confirm red, then revert:
a failing Rust test, a clippy warning, a broken Python assert, a vitest
failure, a `svelte-check` type error. Each must fail the **push-triggered**
run, not only the pull-request one. For OSV, pin a known-vulnerable package
on the branch and confirm a SARIF finding appears, and remove
`continue-on-error` so a scanner crash is red. Then check the scheduled run
actually fires the following Monday.

### macOS pre-flight

Build from a **fresh `git worktree` of the release tag**, not the working
tree. `git status --porcelain` empty is not sufficient assurance given a
stray file has shipped before. Wipe `target/release/jura-trace` and the
`.fingerprint/jura-trace-*` entries for the stale-frontend cache bug.
Checksum `models/` against `src-tauri/models/`. Confirm the updater key is
present at mode 600 and verify the generated `.sig` against pubkey
`1AED7E4A127C6230` yourself before upload. Then install the DMG on a clean
account and run one verify, rather than only launching it.

### Deliberately not tested

No detector accuracy or calibration work, since the model is frozen. No
full Playwright matrix beyond macOS. No Enhanced-mode revocation, reverse
image search, Ollama or Watched Locations, all unchanged. No load testing
of the worker for 145 clients. No history scrub and no dependabot
burn-down inside this window.

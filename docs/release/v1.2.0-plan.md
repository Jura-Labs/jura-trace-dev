# Jura Trace v1.2.0 release plan

**Target: Friday 20 November 2026.** The reasoning for that date is in
"Sequence and the date" below, and it is the first thing to argue with.

**Version v1.2.0**, decided by Paul at the terminal on 10 September 2026
after the checkpoint review put the question. Watermarking becomes v1.3.0.
Decision record: `~/jura-brain/decisions/2026-09-10-trace-follow-up-release-is-v120.md`.
The same decision is recorded as a dated amendment at the foot of
`docs/release/v1.1.0-plan.md`.

Written 10 September 2026 against `main` at `594f67bb`, a few hours after
v1.1.0 was published. Every status below was checked against the code, the
workflow files, the GitHub Actions history of `Jura-Labs/jura-trace-dev`,
the live release assets on `Jura-Labs/jura-trace` and the live updater
endpoint. Nothing here is carried forward on the v1.1.0 plan's word. Where
that plan and the code disagree, the disagreement is named.

## What v1.2.0 is for

v1.1.0 made Jura Trace maintainable. It gave the product a delivery
mechanism that can reach the people who already have it, restored Linux,
put four months of security fixes in front of users, made CI mean something
and made the source public. None of that changes what the application does
when somebody opens a file. v1.2.0 has to. Concretely, "better" means four
things a user would notice. A Windows user stops waiting between ninety and
two hundred seconds for the Analysis Engine on every single launch, which
is the single worst thing about the product for roughly two thirds of the
people who install it. Everyone downloads about a third less, because a 242
MB text encoder that exists to compute a ten kilobyte constant array stops
shipping. Anyone who needs to hand their work to someone else can export a
Verification Record, a signed, self-describing account of what was examined
and what each detector reported, rather than a screenshot. And anyone who
wants to run Jura Trace over a directory, from a script, or on a machine
with no display gets a headless API to do it with, which is the precondition
for the command line tool that two independent adoption reviews named as the
single change most likely to bring new users.

Underneath those four, v1.2.0 has one job that is not a feature and cannot
be skipped: it has to be the release that the release pipeline actually
produces. v1.1.0 was assembled by hand. That is stated plainly in the risks.

## What changed on 10 September, and what this plan is verified against

v1.1.0 is live. `gh release view v1.1.0 --repo Jura-Labs/jura-trace`
reports `isDraft: false`, published `2026-09-10T18:59:34Z`, thirteen assets.
The live manifest at `https://juralabs.org/api/updates/latest.json` returns
version 1.1.0 with three platform blocks, `darwin-aarch64`, `linux-x86_64`
and `windows-x86_64`, carrying inline minisign signatures of 408, 424 and
420 characters. That is the first manifest in the product's history with a
Linux entry and with signatures rather than URLs in the `signature` field.

Two facts about how it got there shape this plan more than anything else.

**The release workflow has never completed a release.** `release.yml` has
three runs, ever, and all three failed: 34470287893, 34496913804 and
34502723812. On the tag run, 34496913804, the Windows build succeeded
(job 102937666349, 46 minutes 37 seconds, and that is the first proof that
the Azure Trusted Signing credentials work on this repository), the macOS
job failed at "Phase 5 per-file sign nested sidecar-bundle code" with
`Process completed with exit code 1` and no stated reason, and the Linux
job failed at "Install Tauri CLI" with exit code 101 for a cargo cache
collision that had nothing to do with the code.

**The last four assets and the publish itself happened outside CI.** There
is no Actions run in `Jura-Labs/jura-trace-dev` after `17:59:33Z`.
`Jura-Labs/jura-trace` has never run a workflow at all. The DMG was attached
at 18:26:59, the updater archive at 18:28:56, its signature at 18:30:59,
`SHA256SUMS.txt` at 18:34:41, `latest.json` at 18:57:51 and the release was
published at 18:59:34. All of that was done by hand.

The v1.1.0 checkpoint of the same date
(`docs/release/v1.1.0-checkpoint-2026-09-10.md`) verified much of the
feature scope against the code and this plan builds on it. It is corrected
in three places, in the "Where this plan contradicts the v1.1.0 plan"
section.

## Scope

Tiers, and what they mean here.

- **Tier A.** The release is not trustworthy without these. They are not
  negotiable and they are not the interesting work.
- **Tier B.** The four items that make this a minor release rather than a
  patch. These are what gets cut at the checkpoint if velocity is short,
  in the order given.
- **Tier C.** Debt. Taken as capacity allows, in the order given, and the
  first thing to stop when Tier A or Tier B is at risk.
- **Cut.** Named, dated and argued in "What is explicitly out".

Three of these items have their own design documents being written in
parallel: the headless API, the Windows packaging and size work, and the
dependency debt. Their estimates below are deliberately ranges and their
open questions are cited rather than answered here.

**Where I think the old estimates are wrong, and why.**

*B1, Windows `--onedir`, 2 days to 3 to 4.* The v1.1.0 plan describes this
as "porting the macOS JTV-184 fix across". The macOS fix was five commits
and it created `release.yml`'s entire Phase 5, a per-file signing loop over
a nested tree, plus a launcher stub, plus a `sidecar-bundle/` resource, plus
a CI verification gate on nested signing. That Phase 5 is the step that
failed the v1.1.0 macOS build. On Windows the equivalent work is not a port
but a second implementation against a different signing service (Azure
Trusted Signing, which currently signs one file) and two installers (MSI and
NSIS) whose resource layouts differ. Two days is the estimate for the easy
half.

*B3, Verification Record Export, timeboxed 2 days to 3 to 4.* The v1.1.0
plan's own gate item 3 requires the export to be produced, its signature
verified with an independent tool, one byte tampered, and verification
observed to fail. That gate implies a signing key, a documented verification
procedure a third party can follow, and a format stable enough to be worth
verifying. Two days builds the export. It does not build the thing the gate
describes.

*B4, size work, 1 day to 1.5 to 2.5.* The backlog file names the real work
itself: proving the precomputed embeddings are bit-identical to runtime ones
on each platform, when onnxruntime versions differ across platforms and the
developer's host runs a different version from CI (SR-21). If a platform
diverges, the fallback is to ship the encoder for that platform only, which
is a build-matrix change. The precompute is an afternoon. The gate is not.

*B2, headless API.* The v1.1.0 plan's 5 to 6 days covered the API and the
CLI together. Splitting them, 4 to 6 for the API alone is not a reduction:
the backlog file is clear that the Axum server is the easy part and the work
is making a headless binary own the sidecar process lifecycle, which today
belongs to `spawn_sidecar` in `src-tauri/src/state.rs` and runs because a
desktop window ran. The design document will refine this. Two questions it
must settle are already open: whether `--api` on the desktop binary is
implemented or deleted from `docs/API_WRAPPER.md:95-109`, and the fact that
`docs/decisions/jura-cli-binary-name-reservation.md` reserves a repository
on Codeberg, which W37-1 has retired. The binary name `jura` is unaffected.

### The two 10 September release-day defects

Both are real, both are still on `main` at `594f67bb`, and both are inside
A1 above rather than being separate items, because they are the same defect
seen twice: the release pipeline asserts less than it appears to.

The first is A1a. The publish step is gated on `needs.build.result ==
'success'`, and the only reason a `v*` tag push does not auto-publish a
release with no macOS disk image is that the macOS CI job fails. The
comment at `release.yml:2186-2190` already says this out loud. It is worth
being precise about why it matters: the checkpoint established that
publishing the draft **is** go-live, because the Cloudflare worker builds
the manifest from `releases/latest` (`index.ts:370-376`). A published
release with no `darwin-aarch64` block tells every macOS install it is up
to date, indefinitely, with no error anywhere. The completeness assertion at
`release.yml:1873` catches this and fired correctly three times on 10
September, but it gates the workflow's own publish step, not a person
pressing Publish on a draft. So today there are two guards, one of which is
a failure and the other of which a human can walk past.

The second is A1b. The published `SHA256SUMS.txt` lists five installer
artefacts and omits `Jura.Trace.app.tar.gz`, the updater archive, which the
workflow's own `installerExts` at `release.yml:1558` includes. The archive
was attached at 18:28:56 and the checksum file at 18:34:41, four minutes
later, so it was present. The one file the updater downloads on the user's
behalf is the one file with no published checksum.

The fix for both is the same shape and it is the shape that already works
elsewhere in this workflow: assert what you require rather than depending on
something else failing. Gate publish on the platforms present, not on a
build result. Assert that every installer artefact attached to the release
appears in `SHA256SUMS.txt`, exactly as the manifest completeness assertion
asserts that every platform appears in `latest.json`.

## Sequence and the date

Paul works about 3.5 days a week on Trace.

| | Days |
|---|---|
| Tier A | 5 to 6.5 |
| Tier B | 11.5 to 16.5 |
| Tier C, excluding C7 | 5 to 7.5 |
| Release week: freeze, local macOS build, the gate | 2.5 to 3 |
| **Total** | **24.5 to 33.5** |

At 3.5 days a week that is **seven to ten weeks**. Counting from Monday 14
September, ten weeks ends on **Friday 20 November 2026**.

**Why 20 November and not sooner or later.**

Q4-2 measures two releases and three-platform CI green by 30 November.
v1.1.0 is the first. 20 November leaves seven working days of margin before
that boundary, so a one-week slip costs schedule rather than the measure.
27 November would leave three days and no room; 13 November, the date the
v1.1.0 plan was carrying, sits at the optimistic end of this range and
therefore repeats the mistake that plan diagnosed in itself: "each of the
first two was set at the optimistic end of its range and neither survived
contact".

Taking the pessimistic end costs nothing if the work goes well. It is also
the only end that is honest about what week one contains, which is not
v1.2.0 work at all: the live updater leg on real installs, the
announcement, the re-download notice, and the correction of the
`Jura-Labs/jura-trace` download README, which still lists
`Jura.Trace_0.9.0_aarch64.dmg` and says "Linux is paused for v1.0" while
the release page it sits above now carries an AppImage.

**The discipline that failed last time, and what changes.** The v1.1.0 plan
had a checkpoint and a cut list. The checkpoint happened, a week early, and
was good. The cut list was never applied, because on each of three occasions
the date moved instead of the scope. That is why the feature half of v1.1.0
did not ship: not because the estimates were wrong, but because nothing ever
forced a choice. So: **the date does not move. Scope absorbs everything.**
The cut order is B4, then B3, then B2, then B1, and Tier C stops before any
of them is touched.

## The release gate

Adapted from `docs/release/v1.1.0-plan.md`'s gate and corrected by what
happened on 10 September.

**The single non-negotiable is unchanged: the live updater leg on real
installs before any announcement.** For v1.2.0 it changes shape in one
respect and gains a leg.

- macOS and Windows update **from v1.1.0**, not from v1.0.0. On macOS this
  is the first update where the relaunch fix is in the *running* code, so
  it must complete unattended. The staging leg proved this on 10 September
  at 08:28:15, pid 28116 becoming 28254, but only against a relabelled
  archive.
- **Linux joins the gate, and it can only join now.** Tauri v2's Linux
  updater installs AppImages, v1.1.0 is the first release ever to carry one,
  so v1.1.0 to v1.2.0 is by construction the first Linux update that can
  exist (BL-REL-003, "Update, 10 September 2026"). A failure here is a first
  observation, not a regression.

## What is explicitly out, and why

**Watermarking is v1.3.0, and the reason is the operating envelope, not the
schedule.** BL-WM-001's robustness report, generated 21 March 2026 over 20
images at medium strength with an 11-byte payload, records 100 per cent
survival on original PNG, JPEG Q95 and Q85, and **0 per cent at JPEG Q70,
JPEG Q60, resize 75 per cent, crop 20 per cent and screenshot simulation**.
There is no intermediate band; it goes from 100 to 0 between Q85 and Q70.
The feature exists as a backstop for a stripped Content Credentials
manifest, and the four ways manifests actually get stripped in the wild are
platform recompression, screenshot, crop and download. Those are the four
columns reading zero. A longer release window does not move a cliff. If it
ships in v1.3.0 it ships with that envelope stated plainly in the UI, which
BL-WM-001 estimates at 8 to 12 days including vendoring `imwatermark` so its
eager rivaGan import stops dragging torch into the bundle and doubling it to
1.5 GB. Separately and much cheaper: the two published web pages that claim
watermarking today should be corrected regardless, which is an afternoon and
is already queued as item 6 of the site-update bundle. Shipping the feature
and correcting the pages are alternatives, not a sequence.

**The CLI is v1.3.0.** The locked architecture is a thin REST client over
the headless API, so the API is the CLI's precondition. Shipping the
precondition in one release and the client in the next is the ordering the
architecture already implies, and it removes the item most likely to expand
from the release with the least room. The binary name `jura` stays reserved.

**Full PDF document mode is v1.3.0**, and this is the cut I would most
expect an argument about, so here is the case.

The honesty defect that made BL-DOC-001 urgent is closed. v1.1.0 shipped the
drag-and-drop gate: `ui/src/lib/supportedFormats.ts` now defines nine image
extensions and both the picker and both drop paths read it, so a dropped PDF
no longer runs a pipeline the help page denies. The picker and the help page
agree. What remains is therefore a feature competing on value, not a
correction, and against the headless API it loses.

It has also become more expensive since BL-DOC-001 was written, in a way
that file cannot know. That file is written against c2pa 0.79.3 and lopdf
0.34. The tree is now c2pa **0.90.20** and lopdf **0.42.0**
(`src-tauri/Cargo.lock:799-800` and `:4056-4058`). The `pdf` feature still
exists at 0.90.20 and is defined as `pdf = ["dep:lopdf"]`, but c2pa 0.90.20
requires **lopdf 0.44.0**, and `src-tauri/Cargo.toml:93` pins `lopdf =
"0.42"` for `pdf_provenance.rs`. Those two requirements do not unify under
Cargo's 0.x caret rules, so enabling the feature either carries two copies
of a PDF parser in the binary or moves `pdf_provenance.rs` to 0.44 in the
same change. Read-only remains the ceiling either way: `pdf_io.rs:23` in
0.90.20 still holds `static WRITE_NOT_IMPLEMENTED: &str = "PDF write
functionality will be added in a future release"`.

And there is a claims surface. The C2PA conforming products listing is
scoped to still images, JPEG, PNG, TIFF and WebP. A PDF document mode
requires suppressing the conformance badge on PDF results and re-scoping
every piece of copy that mentions it, in a product whose recurring defect
class is exactly claims outrunning code. That work is right to do. It is not
right to do in the same release as a dependency conflict, a new binary
target and a Windows packaging change.

**winget, the Homebrew tap and AUR are decoupled from the release, not
deferred.** The v1.1.0 plan held a "channels week" for them. They do not
need one: a winget manifest and a Homebrew cask point at release assets that
already exist, so they can be submitted the week after v1.2.0 publishes,
against v1.2.0's assets, without occupying a day of the critical path. Two
to three days of work, zero of them in the release. Note one real risk when
they are attempted: the MSI is around 740 MB, and B4 is what makes these
channels a comfortable proposition rather than an argument with a reviewer.

**scikit-learn 1.9.0 is v1.3.0 unless an advisory forces it.** Dependabot
PR #5 was closed because `deepfake_classifier.joblib` raises
`ModuleNotFoundError: No module named '_loss'` under 1.9.0. Fixing it means
re-serialising the production GBM and updating both SHA-256 constants, which
is a model change, which means re-running the calibration corpus to show
verdicts unchanged. v1.2.0 is otherwise not touching the model and that is
worth keeping true.

**reqwest PR #25 is v1.3.0 unless an advisory forces it.** 0.12.28 to
0.13.2 makes rustls the default TLS backend instead of native-tls, changes
the crypto provider from ring to aws-lc, and switches root certificates to
`rustls-platform-verifier`. BL-TEST-001 established that
`rustls-platform-verifier` genuinely consults the Windows trust store, which
is what makes the updater work there. Swapping the default TLS backend in
the release that first has to prove Linux auto-update is the wrong order for
the same reason C1 goes in week one: pipeline-shaped changes need runway.

**Unchanged and still out:** ProofMode, the GBM v5b retrain, Conformant
signing (the blocker is an unresolved identity model, not time), ADJPEG,
PRNU, SynthID, model download on first run, quantisation, Flathub, Snap and
an apt repository.

## Risks, ranked

Each of these is a risk rather than a worry because there is an observation
behind it, not a feeling.

**1. The release pipeline has never produced a release, and v1.2.0 is
planned as though it will.** `release.yml` has three runs and three
failures. v1.1.0's macOS disk image, updater archive, signature, checksum
file and manifest were all uploaded by hand between 18:26:59 and 18:57:51 on
10 September, and the release was published by hand at 18:59:34, with no
Actions run in the repository after 17:59:33Z. Every estimate in this plan
assumes a working pipeline at the end of it, which is why A1 is week two and
not week nine. If A1 slips, the release week is a manual assembly again and
the gate items that depend on the workflow asserting things cannot be met.

**2. The live updater leg has not passed on any platform.** BL-REL-002 step
3 is open. No client has ever verified a Windows updater signature end to
end, and the fix for the signing order (minisign before Azure rewrote the
MSI in place) is in v1.1.0's build but unproven by any client. v1.1.0 was
published about 45 minutes before this plan was written, so it may have
passed since. If it has not, then the premise of v1.2.0, that features
reach installed users, is unproven, and that is a bigger question than any
item in the scope table.

**3. Windows `--onedir` touches the installer and the signing path in the
release that must prove the updater.** The macOS equivalent created
`release.yml`'s Phase 5, and Phase 5 is the step that failed the v1.1.0
macOS build (job 102937666162, exit code 1, no reason given, because
`release.yml:941` sends `codesign` stderr to `/dev/null`). On Windows the
same change means handing Azure Trusted Signing a nested tree it does not
currently sign, across two installer formats. Mitigation: B1 lands in the
week of 19 October, four weeks before the freeze, and A1d merges PR #2
first so a failure in that family says what it is.

**4. The headless API is the largest single estimate and has two undecided
design questions.** Whether `--api` on the desktop binary is implemented or
deleted from `docs/API_WRAPPER.md:95-109`, and what
`docs/decisions/jura-cli-binary-name-reservation.md` says now that the
repository half of it names Codeberg. The backlog file is explicit that the
Axum server is not the work; owning the sidecar's process lifecycle outside
the Tauri setup path is. Mitigation: it goes first, in the week of 5
October, and the 15 October checkpoint asks about it by name.

**5. The one file the updater downloads has no published checksum.**
`SHA256SUMS.txt` omits `Jura.Trace.app.tar.gz`. This is A1b and it is cheap
to fix, but it is listed as a risk because of what it indicates: the
checksum file is a snapshot of whatever happened to be attached when a step
ran, and nothing asserts that it covers what shipped. The same shape of
absence is what let Linux vanish from the manifest for four months.

**6. Dependency debt is 18 open Dependabot PRs and every sidecar one is
red.** BL-DEPS-004's guard means each pip PR fails Repo hygiene until its
`requirements.lock` is regenerated, which is the correct signal and also
makes each of the ten pip PRs a manual four-file operation. The queue is no
longer saturated, so this is a throughput problem rather than a blockage.
The two that carry genuine behaviour risk are #22 rcgen, because it makes
the per-install local CA behind Sovereign-mode signing, and #19 rusqlite,
nine minors of the database layer.

**7. The size work's gate can fail in a way that costs a build-matrix
change.** BL-SIZE-001 requires the precomputed embeddings to be bit-identical
to runtime ones on every platform, and SR-21 records that onnxruntime
versions differ across platforms and that the developer's host differs from
CI. The documented fallback is to ship the text encoder on the diverging
platform only, which is a per-platform resources list in a release that has
already changed how one platform packages its sidecar. Mitigation: B4 is
first on the cut list and sits a full week clear of the freeze.

**8. `installer-test.yml` has never run, so the whole installer leg is
unexercised.** Zero runs, and A1c explains why it cannot run where it is.
Its install half is untested even in design: nothing downloads the
advertised build, checks its minisign signature, runs the installer and
checks the version afterwards, and the Windows signing-order fault lives
entirely in that untested half. BL-TEST-001 defers that increment to "the
release after next", which is this one.

**The checkpoint expected the release run to fail only at the macOS Phase 5

**The install base has grown.** BL-REL-002 works from 145 downloads. The
v1.0.0 assets now report 190 installer downloads: MSI 93, DMG 42, NSIS exe
28, deb 27. Windows is 64 per cent, which is the figure the `--onedir`
argument rests on, and it holds on the fresh numbers.

**The premise that fewer, larger releases are cheaper deserves revisiting.**
The v1.1.0 plan's build-cost arithmetic is sound: a clean two-platform
release costs about 180 charged Actions minutes against a 3,000 minute
monthly allowance. But the plan drew from it a batching strategy, and the
outcome of that strategy was a release that shipped its floor and none of
its features, twice over. The cost that dominated was not Actions minutes.
It was that a large batch has no forcing function. This plan keeps the batch
and adds the forcing function: a fixed date, a named cut order and one
checkpoint that is allowed to cut.

# Jura Trace v1.1.0 checkpoint review, 10 September 2026

Written 10 September 2026 against `main` at `e7355b40`, from the code, the
GitHub Actions history of `Jura-Labs/jura-trace-dev`, the live updater
endpoint, and the local build output on the SSD. It is the review the plan
scheduled for Thursday 17 September, brought forward because Paul is
considering publishing v1.1.0 today or tomorrow rather than on Friday
13 November.

The plan is `docs/release/v1.1.0-plan.md`. Nothing in it, and no decision
record, has been edited by this review. Paul decides; this proposes.

## Summary

**The floor is done except for the two things that can only be done after
publishing, and one that has never run on this repository.** Everything in
the plan's go/no-go "must be true" list is met or nearly met, with one
exception that is a wording problem rather than a work problem: `ci.yml`
runs on `ubuntu-latest` only, so "three-platform CI green" has never been
true here and will not become true by waiting.

**Publishing on 10 or 11 September is technically available.** The release
that would go out is the repair release the plan describes: a working
updater, a startup update check, an app that restarts itself after an
update, Linux restored, the in-app source link repointed, and four months of
security fixes reaching users for the first time. That is the release's
stated reason to exist and it is ready.

**What would not ship is the second half of the plan.** The Verification
Record Export, full PDF mode, all of Tier 2 and Tier 3, the Windows
`--onedir` retention fix, the headless API and CLI, the packaging channels
and the 356 MB size work are all not started. The plan's own "What ships"
section promises the export and PDF document mode, so those release notes
cannot be used as written.

**Three things stand between a tag and a publish, and none is optional.** A
CHANGELOG section on the release commit, because the release body is built
from the first heading in `CHANGELOG.md` and without one the v1.1.0 page
carries the 8 June rc.30 entry. A Windows release build, which has never run
on this repository. And a macOS DMG rebuilt from the release commit, because
the candidate on the SSD was built at 22:02 on 9 September and the in-app
source link changed on `main` at 10:38 on 10 September.

**Publishing is not announcing.** The plan's single non-negotiable, the live
updater leg on real v1.0.0 installs on macOS and Windows, can only be run
after the assets and the manifest are live. Publishing quietly is what makes
that test possible. Announcing before it passes is what the plan forbids.

**Recommendation: tag and publish on Friday 11 September, not today, and
announce only after the live leg passes.** The reasoning and the alternative
are in the last section.

the assets and the manifest are live. That is the reason publishing and

### The Windows signing order, which is the reason the live leg is the gate

BL-REL-002's second fault was that `release.yml` minisigned the MSI, verified
the signature, and then let Azure Trusted Signing rewrite the MSI in place.
That is fixed in tree: the gate and the re-sign now run after Azure
(`release.yml:1262-1272`, "The re-sign and the gate now run after Azure ...
on the bytes that actually ship"). **No published release has been built
with that fix.** The 7 September smoke on `jura-archive` did produce
Windows assets with it, and `updater-e2e` drove the real MSI, but no client
has ever verified a Windows updater signature end to end. That is the single
most likely thing to fail on the live leg, and it is why the live leg is the
gate rather than a formality.

The other three merges since PR #53 (`df95a269`, `a2ed11ba`, `b3f80e84`,

`TRAINING.md`, `.gitignore`, the backlog, the plan and

exist (CHANGELOG included), a fresh `git worktree` of the tag rather than a

which is BL-REL-001's fix), notarisation, and a `.sig` verified against
`1AED7E4A127C6230` before upload. Budget 25 to 40 minutes plus notarisation,
and expect the staging leg to be worth re-running against the new archive,
because the archive is regenerated from a re-signed `.app` in Phase 6 and
Phase 6.5 checks it.

is dated 11 June 2026 and its release flow still begins "Push tag to

1. **The Windows release build has never run on this repository.** The
   Azure signing secrets are present at repository level
   (`AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TENANT_ID`,
   `AZURE_SIGNING_ACCOUNT`, `AZURE_SIGNING_ENDPOINT`, `AZURE_CERT_PROFILE`),
   and `RELEASE_PAT` was replaced today and proven by the Linux run
   creating a draft and uploading to `Jura-Labs/jura-trace`. Neither
   observation is a Windows build. The last one was 7 September on
   `jura-archive`.
2. **The Windows updater signature has never been verified by a client.**
   See the signing-order note above.
3. **The NSIS duplicate install is unresolved and would go live.** 23
   installs from the NSIS exe, one `windows-x86_64` manifest key, an MSI
   offered to all of them.
4. **`installer-test.yml` has never run here**, so both the live manifest
   contract test and the NSIS assertion are unexercised on this repository.
5. **The release notes as the plan writes them are wrong for this
   release.** They promise the Verification Record Export and PDF document
   mode. Publishing with that text would be the BL-CLAIM class of defect,
   committed on purpose.
6. **Two stale in-app promises would ship**: the Article 50 export "planned
   for the v1.0.1 release (~early August 2026)" and the "Jura Trace v1.0"
   self-description in four places.
7. **A rushed CHANGELOG is a release-body problem, not a documentation
   problem.** It is what the public page shows.

None of these is a reason not to publish. Each is a reason to publish
deliberately rather than today.

## Recommendation

**Tag and publish on Friday 11 September. Do not tag today. Do not announce
until the live leg passes on both macOS and Windows.**

The reasoning:

The release's stated single measure of success is that a person running
v1.0.0 receives it without being told to. Everything required for that is
done and proven as far as it can be proven without publishing: the manifest
is correct and live, the startup check exists, the relaunch works, the
archive is signed properly, and the staging leg passed twice. The remaining
proof is the live leg, and the live leg is blocked on publishing. Waiting
until 13 November does not make that test possible any sooner; it only
leaves 145 installs carrying five reachable advisories for nine more weeks.
That is the strongest argument for going now, and it is a good one.

The reason not to go **today** is not doubt about the work. It is that the
publish day has four sequential dependencies that do not exist yet and one
that has never been exercised. The CHANGELOG is being drafted in parallel.
The macOS DMG has to be rebuilt from a commit that does not exist. The
Windows build has never run here. And the release notes have to be rewritten
because the plan's "What ships" list describes a release that is not this
one. Attempting all of that plus a 72 minute Windows build and a 40 minute
macOS build inside the remainder of a Wednesday is how the 19 June release
day cost 240 charged minutes in cancelled runs. One day of preparation costs
nothing against a November date that has already moved twice.

So: spend the rest of today on the release commit. Land the CHANGELOG with
the quit-and-reopen sentence in it. Decide the four "Jura Trace v1.0"
strings and the `help/compliance` Article 50 sentence, both of which are
single-line edits and both of which are claims the product makes about
itself. Rewrite the "What ships" list to describe this release. Then on
Friday morning run steps 2 to 9, and Friday afternoon and the weekend run
steps 10 to 13 with a pristine v1.0.0 on each platform.

Announce when the live leg passes, not before, and send the re-download
notice at the same time. If the live leg fails on Windows, which is the
likeliest single failure given the signing-order history, the assets are
already up and the fix is a Windows-only re-dispatch rather than a whole
release day.

One thing to decide separately, because it is not a release question: what
the follow-up release is called. The list it would inherit is most of the
plan, not a patch.

## The alternative, if Paul chooses otherwise

**If he publishes today**, the order in the table above still holds and
nothing in it can be skipped, but three things should be traded rather than
rushed:

- Write the CHANGELOG section short. Six bullets and the quit-and-reopen
  sentence is enough, and a short honest entry beats a long one assembled
  under time pressure. It can be expanded on the release page afterwards,
  since the body is editable text.
- Accept the four "Jura Trace v1.0" strings and the Article 50 sentence as
  known defects, record them in `backlog/BL-CLAIM-002` as shipped, and fix
  them in the follow-up. Do not attempt them on the same afternoon as a
  release build.
- Do not attempt the live leg tonight. Publish quietly, purge, run the macOS
  smoke, and leave the pristine installs to ask in the morning. The plan's
  rule is that the announcement waits for the live leg, and that rule is
  what makes a quiet publish safe.

**If he holds to the plan's 13 November date**, the checkpoint's honest
finding is that the floor finished nine weeks early and the second half of
the scope has not started. That is not a reason to hold. It is a reason to
publish the repair release now and re-plan the rest as its own release with
its own date, which is what the plan's cut list was already pointing at.

**If he wants a middle path**, publish v1.1.0 on Friday as recommended and
keep 13 November as the date for the second release rather than for a small
patch. That satisfies Q4-2's two-release measure with real runway instead of
seventeen days, and it removes the pressure that made the November release
"deliberately small" in the first place. That is a change to a plan and a
quarterly measure, so it is Paul's call and not this review's.

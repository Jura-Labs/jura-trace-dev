# BL-REL-007: the checksum file omits the one file the updater downloads

**Status**: Open. Found 11 September 2026, checking the published v1.1.0
assets while planning the v1.2.0 release work.
**Raised**: 11 September 2026
**Severity**: Medium. Nobody is misled, because the file does not claim to
be complete. But the release notes send users to it to verify their
download, and the largest artefact on the release, the one the auto-updater
fetches on their behalf, is the one with no published hash.

## What is wrong

`SHA256SUMS.txt` on the v1.1.0 release is 510 bytes and lists five
artefacts:

```
15d3d9f5670097986c5cb5db2625befe502b32aed2c55fbaa47315514283539c  JuraTrace-1.1.0-Linux-x86_64.AppImage
e83c70fc73d029f2252158da0a5a5ab4be2fcabf715e6b3651cf95ff1ba3a339  JuraTrace-1.1.0-Linux-x86_64.deb
5c3648cb9e929384da2f8567ea582997d6c7f70db0b48a1a67b8eb7c96a7dab7  JuraTrace-1.1.0-macOS-AppleSilicon.dmg
1b23bbfe603ad50becaf14c704377dcbb760335b9cad976fad0b258a45b0df7c  JuraTrace-1.1.0-Windows-x64-setup.exe
e240d0a118b92ae983ff51d786a0d4229112410118ab9fb32d75309e3ce70e4e  JuraTrace-1.1.0-Windows-x64.msi
```

The release also carries `Jura.Trace.app.tar.gz`, 855,832,536 bytes. It is
the largest asset on the release and it is what the macOS auto-updater
downloads and installs. It has no line in the file.

**The filter is right and the file is wrong.** That is the question this
item was asked to settle, and the evidence settles it.
`.github/workflows/release.yml:1558` is:

```javascript
            const installerExts = ['.dmg', '.msi', '.exe', '.AppImage', '.deb', '.tar.gz'];
```

`.tar.gz` is in the list, and `Jura.Trace.app.tar.gz` ends with it. Had the
workflow written this file, the archive would be in it.

**Which means the file was not generated by the workflow.** The archive was
attached at 18:28:56Z and `SHA256SUMS.txt` at 18:34:41Z, four minutes
later, so the asset was present when the file was written. There is no
Actions run in the repository after 17:59:33Z and both release runs report
`run_attempt: 1`, recorded at `docs/release/v1.2.0-plan.md:612-618`. So
`SHA256SUMS.txt` was produced outside the workflow, by hand, from a list
somebody wrote down.

**And nothing would have noticed either way.** The step at
`:1531-1626` has one floor, added on 10 September after it wrote a one-byte
file over a good one: it fails if `toHash.length === 0` (`:1569-1577`).
There is no assertion anywhere that the file it produced covers the
artefacts that are attached. The equivalent assertion for the update
manifest does exist, at `:1949-1977`, and it fired three times on 10
September doing exactly its job. The checksum file has no counterpart.

**v1.0.0 shipped the same omission, and one more.** Its `SHA256SUMS.txt`
lists four artefacts: the `.deb`, the DMG, the NSIS installer and the MSI.
No updater archive, and no AppImage, because none was built, which is
BL-REL-003.

## Verified, not inferred

Fetched from the public release on 11 September 2026.

```
$ gh release download v1.1.0 --repo juralabs/jura-trace --pattern SHA256SUMS.txt
$ wc -l SHA256SUMS.txt
       5
$ gh api repos/juralabs/jura-trace/releases/tags/v1.1.0 \
    --jq '.assets[] | "\(.name) created=\(.created_at)"'
Jura.Trace.app.tar.gz created=2026-09-10T18:28:56Z
...
SHA256SUMS.txt created=2026-09-10T18:34:41Z
```

- The archive's size, 855,832,536 bytes, from the same listing.
- `.github/workflows/release.yml:1558`, the `installerExts` array.
- `:1569-1577`, the empty-set floor, which is the only assertion in the
  step.
- `:1949-1977`, the manifest completeness assertion, for contrast.
- `.github/workflows/release.yml:173`, the release-notes line that sends
  users to the file:

```
          **Verify your download:** grab **[SHA256SUMS.txt](${base}/SHA256SUMS.txt)** and run `shasum -a 256 -c SHA256SUMS.txt` ...
```

- `docs/install-guides/verify-downloads.md:26-58`, the published guide,
  which tells the reader that "each file listed in `SHA256SUMS.txt` that is
  present in the current directory will be checked".
- The v1.0.0 file, four lines, fetched the same way.

## Who it affects, and how badly

Two groups, and neither is badly harmed.

Anyone verifying a download by hand is fine: they downloaded an installer,
and every installer is listed. `shasum -c` skips files it has no line for,
so the command in the release notes reports OK and says nothing about the
archive.

Anyone who wants to verify what the updater fetched, or to mirror the
release inside an institution that requires a published hash for every
binary it distributes, cannot. `docs/install-guides/windows-it-deployment.md:263`
points IT departments at this file for exactly that purpose. For a
provenance product, publishing checksums for five of six binaries and
saying nothing about the sixth is a poor look independent of the risk.

The updater does not rely on the checksum file, so the integrity of an
update is not affected by this. The archive is covered by a minisign
signature (`Jura.Trace.app.tar.gz.sig`) that the Tauri updater verifies,
and BL-REL-002 is the item about that path. This is about what is
published for people, not about what the updater checks.

## What to do, in order

1. **Assert coverage, in the workflow.** After writing the file, list the
   release's assets, filter with the same `installerExts`, and fail if any
   of them has no line. That is the manifest completeness assertion applied
   to checksums, it is about fifteen lines, and it is the step that makes
   everything below unnecessary to remember. Do this first.
2. **Regenerate `SHA256SUMS.txt` for v1.1.0** and replace the published
   file, so the archive that users already have has a hash they can check.
   `gh release upload --clobber` is already how the step uploads it.
3. **Decide whether the manual path stays.** Today macOS artefacts arrive
   after the workflow has finished, so the checksum step either runs before
   they exist or has to be re-run. If the checksum step is to be trusted,
   it has to run last, after every asset is attached. That is the same
   ordering problem as BL-REL-006 step 1 and it has the same answer:
   assert what is required, and run the assertion on the bytes that ship.
4. **Leave v1.0.0 alone.** Its file is incomplete for two reasons and one
   of them, the missing AppImage, is that the artefact never existed.
   Rewriting the checksums of a superseded release is not worth the risk of
   changing a published artefact; note it in BL-REL-003's history instead.

## What not to do

- **Do not remove `.tar.gz` from `installerExts` to make the file
  consistent with itself.** That is the wrong half. The list is right; the
  published file does not match it.
- **Do not add the `.sig` files to the checksum file.** They are 400 bytes
  of signature over the artefact and a hash of a signature helps nobody.
  Installers and the updater archive is the right set.
- **Do not wait for BL-REL-006.** They share a cause and a fix shape, and
  this one is a day's work at most. Shipping it first is fine and gives
  BL-REL-006 a working pattern to copy.
